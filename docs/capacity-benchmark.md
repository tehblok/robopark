# Проверка API на 200 пользователей

Проверка от 6 сентября 2026: два настоящих процесса Uvicorn обслужили 200 разных пользователей и сессий через HTTP. Оба профиля ниже прошли критерии, без 5xx, таймаутов и неожиданных ответов. Хост проверки — macOS 26.6.2, ARM64, 10 CPU, Python 3.13.14. Это измерение локального API; производительность Armbian на 8 ГБ или Ubuntu на 32 ГБ нужно измерить на соответствующем компьютере.

| Профиль постоянной активности | Запросов | Длительность | RPS | P50 / P95 / P99, мс | Вызовов внешнего stub |
| --- | ---: | ---: | ---: | --- | ---: |
| 200 клиентов, 20 задач и 20 VIN | 4 000 | 60,043 с | 66,62 | 6,46 / 111,51 / 119,41 | 273 |
| 200 клиентов, 200 задач и 200 VIN | 2 000 | 30,039 с | 66,58 | 9,21 / 225,81 / 230,33 | 999 |

В обоих случаях каждый клиент делает один запрос раз в 3 секунды со сдвигом начала. Чередуются список задач, карточка, комментарии, входящие репорты и диагностика робота. Двадцать клиентов дополнительно создают по локальному репорту вместо одного чтения. Это заданная смесь HTTP-запросов со средней интенсивностью около 67 RPS, а не запуск 200 браузеров и не точное воспроизведение всех таймеров интерфейса.

При 200 разных VIN Emergency stub получил 400 запросов за 30 секунд; при 20 VIN — 111 за 60 секунд. Большое число разных роботов существенно повышает внешнюю нагрузку, хотя локальное API в этой проверке справилось. Stub отвечает через фиксированные 100 мс и не воспроизводит ограничения или сбои настоящих интеграций.

| Холодное открытие списка | 1 183,80 | 200 × 200 OK; один внешний поиск |
| Холодная карточка одной задачи | 778,02 | 200 × 200 OK; одно внешнее чтение |

Последняя стрессовая фаза использует общие карточку/VIN независимо от числа записей в постоянном профиле. Холодные серии показывают объединение одинаковых запросов между процессами. Серии с разными VIN измеряются отдельно в постоянном профиле. Всплески проходят напрямую через localhost и могут превышать допустимую интенсивность публичного туннеля.

Максимальная сумма пиков RSS двух рабочих процессов составила 296,06 МиБ в профиле 20 записей и 304,50 МиБ в профиле 200 записей. Это сумма индивидуальных максимумов, а не одновременная выборка всей памяти машины; родитель Uvicorn, генератор нагрузки, stub, ОС и браузеры сюда не входят. Короткая проверка не измеряет длительное накопление памяти.

## Повторить

Из корня репозитория, с установленными зависимостями API:

```sh
apps/api/.venv/bin/python scripts/capacity_benchmark.py \
  --output /tmp/robopark-capacity-20-records.json

apps/api/.venv/bin/python scripts/capacity_benchmark.py \
  --active-records 200 --duration 30 \
  --output /tmp/robopark-capacity-200-records.json
```

На целевой машине можно увеличить `--duration`, например до 600 секунд. Для задержки интеграций 500 мс используется `--stub-delay-ms 500`. При перегрузке генератор не догоняет пропущенные интервалы дополнительным всплеском; критерий достигнутой интенсивности обнаружит падение RPS. Перцентили включают время HTTP-запроса со стороны генератора, включая очередь; это закрытая модель с паузой после задержавшегося запроса, а не полноценное измерение поступающего потока при насыщении.

Сценарий сам создаёт временную SQLite с WAL, 200 пользователями, 200 сессиями, 200 репортами, двумя парками и синтетическими настройками интеграций. У 5% сессий первый запрос продлевает срок действия записью в SQLite. Работают реальные аутентификация, роли, проверка парков, кеши, сериализация, SQL и lifespan приложения. Заменяются только методы внешних Tracker/Emergency клиентов: они делают HTTP-запросы в локальный stub, который считает фактически принятые вызовы обоих процессов. После завершения осталось 220 репортов, 200 пользователей и 200 сессий; `PRAGMA integrity_check` вернула `ok`.

Сценарий не принимает URL существующего сервера или путь к существующей БД. Подпроцессы получают минимальное явно заданное окружение; `.env` не читается. В рабочем процессе заблокированы сетевые соединения за пределы loopback. После проверки процессы завершаются, а временная БД удаляется. JSON сохраняется по `--output`.

Код выхода 0 означает: все ответы соответствуют контракту; оба процесса обслуживали нагрузку; P95 постоянной активности меньше 1 секунды, всплесков — меньше 5 секунд; достигнуто минимум 90% заданного RPS; холодные одинаковые запросы объединены; чужие данные не выгружались; локальные записи сохранены и SQLite цела. Нарушение любого критерия даёт код 1 и диагностический JSON. Названия фаз содержат `200` для основного профиля; при использовании `--users` действительное число указано в `configuration.users` и счётчиках запросов.

Полные измерения: [20 записей](capacity/2026-09-06-20-records.json), [200 записей](capacity/2026-09-06-200-records.json). Скрипты: [генератор нагрузки](../scripts/capacity_benchmark.py), [изолированный адаптер приложения](../scripts/capacity_app.py).

## Что показал первый запуск

До исправления пула соединений холодная серия из 200 запросов дала 152 таймаута по 15 секунд, а следующая серия — 200 таймаутов. В журнале был `QueuePool limit of size 5 overflow 10 reached`. Авторизация удерживала соединения между этапами обработки, пока другие запросы занимали рабочие потоки ожиданием свободного соединения. Проверка с `NullPool` устранила зависание; финальные измерения выполнены уже с исправлением в production-коде, без замены пула в адаптере нагрузки.

Внешний HTTP-клиент, сеть, фактические задержки Tracker/Emergency, ограничения Tuna, TLS, медиафайлы и рендеринг браузера остаются вне измерения. Успешный локальный результат не доказывает обработку 200 одновременных холодных открытий через туннель и не заменяет повторный прогон на целевой машине.
