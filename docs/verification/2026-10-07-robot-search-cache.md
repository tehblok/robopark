# Проверка ускорения поиска робота

## Причина и измерение

На Khadas запрос владельца с доступом к 12 паркам последовательно выполнял
12 поисков Tracker. Измерение старого rc.39: 11,686 секунды, 12 обращений.

Кандидат rc.40 проверен в отдельном процессе API-контейнера, без подмены
работающих модулей и без отправки сообщений в Telegram. Первый запрос:
2,226 секунды, одно обращение Tracker. Повторный: 0,020 секунды, ни одного
обращения. Обе версии вернули один и тот же набор из шести ключей задач.
Это измерение серверного поиска, без времени доставки Telegram.

## Использование данных и границы

Если уже есть свежая полная выборка реестра по требуемым очередям, поиск
использует её. Старые DTO без полей классификации и неполные аналитические
снимки не считаются полноценной базой карточек. При отсутствии полной
выборки выполняется один запрос по разрешённым тегам каждой очереди.
Для комбинированной выборки, достигшей лимита 500, сохраняется старый обход
парков — частичные совпадения номера не должны вытеснить другой парк.

Отдельный кэш результатов поиска: TTL 20 секунд, до 256 записей / 8 МиБ
в памяти процесса; общий механизм LiveMerge объединяет обращения процессов
и ограничивает своё хранилище. Ключ включает хеш токена, весь запрос,
сортировку, лимиты и разрешённые очереди. Возвращается независимая копия.
Изменение задачи, списков или токена инвалидирует семейство; завершение старого
запроса после инвалидизации не восстанавливает устаревший кэш.

Права роли и назначения парков проверяются заново на каждом обращении.
Номер робота, очередь и тег одного разрешённого парка проверяются вместе.
Сохранены фильтры типа/статуса/решения и исходные приоритеты карточек.

## Локальные проверки

- 61 тест native Telegram и новых сценариев поиска/кэша.
- 100 тестов кэша, реестра роботов, операций Tracker и новых сценариев.
  Эти два запуска частично пересекаются.
- 79 тестов fast gate, web lint и проверка 33 маршрутов.
- 16 тестов версий, документации и совместимости миграций.
- 65 тестов bot service и HTML-карточек.

Новые регрессионные тесты сначала падали на старой реализации: 24 обращения
для двух поисков по 12 паркам, отсутствие использования полной выборки,
неполная проверка пары очередь/тег. После исправления проходят.
Независимое ревью выявило регистрозависимое сравнение очереди; добавлен
отдельный регрессионный тест и нормализация регистра настроек парка.
