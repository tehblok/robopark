# Проверка правила по собранным сигналам

В редакторе правила действие «Проверить собранные ошибки» проверяет текущий
черновик по последним 50 сохранённым исходным сигналам всех парков. Учитываются
состояния `new`, `mapped` и `ignored`. Проверка запускается вручную и не меняет
каталог, разметку, статистику наблюдений или журнал аудита. Сохранение правила
остаётся отдельным действием. Проверка одного введённого примера не меняется.

Результат содержит совпадения, несовпадения и пропущенные образцы. Для совпадений
показываются номера других включённых правил, распознающих тот же образец;
они могут распознавать разные части структурированного сигнала. Редактируемое
правило исключается из этого сравнения. Нет оригинала, повреждение, ограничения
размера/сложности и исчерпанный бюджет означают «пропущено», не «не совпало».
Номера некорректных сохранённых правил выводятся отдельно: пересечения с ними
не проверены. Отключённый черновик не даёт совпадений, как и обычный matcher.

API: `POST /admin/diagnostic-rules/test-samples`, только одобренные встроенные
роли `admin` и `royal`. JSON: `{ "rule": DiagnosticRuleCreate, "limit": 50,
"exclude_rule_id": 123 }`; последний параметр необязателен. Ограничение выборки
1–100, по умолчанию 50. Ответ `no-store` содержит `items`, `matched`, `missed`,
`skipped`, `overlapping`, `limit`, `has_more`, `budget_exhausted`,
`invalid_rule_ids`. Элемент: `id`, `outcome`, `overlap_rule_ids`, `reason`.
В ответе нет исходных значений, путей источников, имён роботов, текстов правил
или пользовательского содержимого ошибок валидации.

Используется общий чистый `diagnostic_rule_matches_sample`: восстановленный
контейнер и пустые позиции массива не считаются оригинальным образцом.
`original_json` разбирается однократно, исходные строки не интерпретируются как
JSON повторно. `raw_json` с остатками после прежней классификации не читается.
Выборка проецирует только ограниченные исходные значения и типизированные пути.
Чувствительные значения и пути отбрасываются повторно перед проверкой.

Ресурсные пределы: до 100 включённых правил (сверх этого явный ответ 422,
`diagnostic_sample_catalog_too_large`), оригинал до 8192 байт, путь до 2048 байт,
32 сегментов и 10000 позиций восстановленных массивов, оригинал до 256 узлов
и глубины 24. Общий вычислительный бюджет проверки образцов — 1 секунда или
2000 операций; учитывается внутри перебора значений общего matcher. Это не
таймаут SQL или всего HTTP-запроса. Сохраняются пределы компилятора regex и
таймаут одного поиска общего matcher. При частичном выполнении результат
прямо отмечается, пересечения незавершённого образца не выдаются как полные.
Клиент ограничивает запрос 20 секундами, не повторяет его автоматически.

Результаты не сохраняются на клиенте и очищаются при редактировании, смене
правила/пользователя/парка, обновлении каталога и сохранении. Запоздалые ответы
отменённого владельца не отображаются. Фоновых запросов функция не добавляет;
существующее скрытие/офлайн-поведение и период опроса каталога не меняются.
Миграция не требуется: используется `original_json`, добавленный в 0021.

Проверки: `tests/test_diagnostic_sample_tests.py` и существующие серверные
регрессии диагностики; web-тесты домена `diagnostics`; Chromium
`e2e/operational/diagnostic-samples.spec.ts` (390/1440 px, доступность,
переполнение, явная публикация). Все используют изолированные тестовые данные.
