## Политика хранения

- После проверенной записи OTA-кэша исходный upload удаляется. Кэш операции
  сохраняется до устойчивой конечной квитанции; активный и неудачно откатившийся
  update удерживает нужные файлы для восстановления.
- Успешная сборка запускает ограничение собственного Buildx builder до 2 GB.
  Образы действующего и предыдущего релиза, а также нужный кандидат защищены.
  Удаление образа выполняется по проверенному image ID; метки сборки позволяют
  после прерывания опознать только собственный кандидат.
- Старые теги с общим image ID, неподтверждённые теги без меток и состояние
  ручного восстановления не удаляются автоматически. Для них нужен точный
  осмотр; `docker system prune` и удаление PostgreSQL volumes не применяются.
- Экран владельца показывает категории диска, включая OTA, релизы, образы,
  BuildKit, резервные копии, диагностику, журналы и PostgreSQL; предпросмотр
  очистки предшествует любому ручному действию.

## Исправления, вошедшие в текущий архив

После создания предыдущего архива дополнительно исправлены резервирование
места для параллельных OTA-загрузок, удаление временной копии после прерывания
финализации, восстановление OTA при заполненном диске, очистка снимка после
успешного отката неудачной попытки и удержание квитанции, пока на неё ссылается
загруженный пакет. После успешной публикации больше не создаётся лишний маркер
`successful-ota/<sha256>.json`: код его нигде не читает; квитанция операции и
маркер релиза остаются. Уже существующие маркеры на хосте не удаляются.
Удаление upload-файла закрепляется `fsync` его каталога до удаления метаданных
и квитанции; временные метаданные после аварийной остановки удаляются по точному
имени и TTL. Host-очистка оставляет входной `.ota`, пока существует его
API-метаданные: срок файла сам по себе не доказывает, что операция завершена.
Плановая копия БД ротирует старые локальные копии сразу после проверки и
надёжной записи новой. Если подтверждение исходного артефакта API не прошло,
следующий запуск сначала повторяет его по сохранённой квитанции и не создаёт
ещё одну копию при повторной ошибке.
Копия после `docker compose cp` дополнительно проверяется как локальный
обычный файл владельца и получает права `0600` до чтения, публикации и `fsync`:
Docker может перенести разрешения исходного файла. Терминальные неудачные
плановые снимки без артефакта освобождают зарезервированное место в индексе,
поэтому восемь последовательных сбоев не блокируют будущие резервные копии.
Плановая очистка сначала удаляет просроченные точные временные OTA-копии,
сохраняя активную операцию, а затем проверяет терминальные пакеты. Это
позволяет восстановиться, если более 512 временных файлов накопилось после
прерываний.
Если накопилось более 512 уже завершённых кэшированных `.ota`, их очистка
идёт партиями по 512: наличие лишнего файла больше не блокирует всю операцию.
Каждый пакет удаляется только при совпадении точной SHA-256-квитанции;
незавершённая операция и неподтверждённые файлы сохраняются. Для сбоя чтения
каталога квитанций предпросмотр очистки показывает блокировку.
Когда кэш пуст, плановая очистка не читает каталог постоянных OTA-квитанций;
при небольшом кэше останавливает чтение, как только все кандидаты проверены.
В PWA ограничен один таймер повторной синхронизации и добавлена
отложенная очистка старой недоступной базы входящих фото, включая запуск до
авторизации. Не ответившая на запрос вкладка больше не перезагружается
принудительно: ожидающий worker активируется после закрытия такой вкладки.

Эти изменения включены в текущий архив. Связанные короткие проверки: 164 host-теста,
62 API-теста, 108 web-тестов, 14 тестов service worker и компиляция TypeScript
прошли; дополнительный host-проход для согласования API upload и host TTL —
112 тестов, и 11 коротких тестов плановой копии. Фактический ARM-хост
и установленная PWA всё ещё не проверены.
После этих исправлений дополнительно прошли 15 целевых тестов резервных копий,
API-снимка и OTA-очистки, а также 150 коротких тестов OTA, хранения и образов;
`ruff` и `git diff --check` прошли.
Последующее ревью выявило ещё два сценария остановки: временный сбой выхода из
maintenance или записи OTA-квитанции после терминального журнала, а также
накопление созданных, но не прошедших проверку плановых снимков. OTA теперь
оставляет команду в состоянии выполнения без ложной конечной квитанции;
повтор по тому же ID завершает выход из maintenance и запись квитанции, в том
числе после смены boot ID, без повторной публикации.
Неподтверждённый снимок удаляется только по точному имени после проверки типа,
владельца, числа ссылок и устройства; каталог синхронизируется до освобождения
записи индекса. Если процесс прервался между удалением файла и обновлением
индекса, следующий запуск освобождает только отсутствующие записи при отсутствии
активного задания; существующие и активные снимки сохраняются.
Короткие проверки: 170 host-тестов OTA/команд и 21 тест host deployment прошли. Для
изменённых Python-файлов, кроме `commands.py`, Ruff чистый; в `commands.py`
остались шесть предупреждений, существовавших до последней правки. Они не
относятся к новым строкам.
Настольная карточка задачи в Playwright проверена по фактическому изображению,
её устаревшие светлый и тёмный эталоны обновлены и повторные запуски без записи
прошли. Мобильные сценарии этой же карточки на ширине 390 px в обеих темах
также прошли без обновления эталонов.
После исправления массового OTA-кэша прошли ещё 93 коротких теста кэша,
retention и предпросмотра хранения; Ruff и `git diff --check` для затронутых
файлов прошли.
Совместный короткий прогон OTA, установки, команд, кэша и Docker-образов:
299 тестов прошли за 4,9 секунды.
Позднее живой экран «Система» показал растянутую карточку метрики. После
падающего браузерного теста общий примитив метрики и выравнивание обзорной
сетки исправлены. Фактический экран осмотрен; шесть адресных геометрических,
16 визуальных сценариев четырёх экранов и TypeScript прошли. Два изменившихся

В локальном демо чтение Tracker сейчас заканчивается `NewConnectionError` к
`st-api.yandex-team.ru`: короткие логи API и worker содержат точный отказ

сетевой guard до проверки токена. Два коротких теста guard прошли: обычный режим

введённые пользователем настройки; его фактические аргументы запуска не
подтверждены. Поэтому живые задачи и работу worker с внешним Tracker эта
демонстрация не подтверждает.
Это не заменяет визуальный проход всех маршрутов и Android PWA.
