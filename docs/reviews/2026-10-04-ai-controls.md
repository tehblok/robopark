# Управление очередью, обучением и очисткой ИИ

Продолжение после rc.27. Только подтверждённые дефекты; runtime остаётся
доступен только на AGX. Формат OTA и схема БД не меняются.

## Подготовка и запуск задания

Подготовка запроса может занимать время. Раньше выполненное во время неё
отключение ИИ или удаление скрипта не мешало перевести ещё ожидающее задание
в исполнение. Регрессии воспроизвели оба случая с настоящими API-изменениями
и отдельной worker-сессией.

Перед claim worker завершает подготовительную read-транзакцию, получает
`ai-controls → ai-knowledge`, повторно читает задание, права, настройки, источники и ревизию
скрипта. Только после этого выполняется CAS `queued → running`. Временная
занятость lock оставляет задачу в очереди: тест с настоящей блокировкой
подтверждает отсутствие исполнения во время ожидания и один запуск после
освобождения. Завершённый результат по-прежнему проверяется перед публикацией.
Уже начатый inference транспортно не отменяется, его результат после отмены
или запрета не публикуется. Тест скрипта не требует готовой языковой модели.

Отдельно воспроизведено зависание `running` при занятости `ai-controls` в момент
сохранения готового ответа. Теперь финализация делает до пяти ограниченных
попыток захватить блокировку, сохраняя готовый результат только в памяти.
На каждой успешной попытке заново проверяются права, настройки и ревизии.
Повторного inference/исполнения скрипта нет. При длительной занятости условный
`running → failed` с `ai_finalize_busy` не публикует результат и не помечает
скрипт проверенным. UI объясняет, что результат не удалось сохранить.

Три регрессии используют реальную блокировку: временная занятость с успешным
сохранением, длительная занятость и удаление скрипта во время ожидания. Временные
сценарии освобождают lock только после фактического первого timeout, без гонки
таймеров. Удаление приводит к отмене; во всех случаях скрипт исполняется один раз.

## Доработка по независимому ревью

Ревью нашло щель между проверкой ревизии источника и фиксацией результата:
изменение знания использует `ai-knowledge`, а прежняя проверка задания держала
только `ai-controls`. Регрессия на настоящем PostgreSQL воспроизвела удаление
после успешной проверки и до commit результата. Теперь claim и публикация
удерживают обе блокировки в общем порядке; изменение знания ждёт завершения
транзакции. Если оно уже завершилось до проверки, результат отменяется.

Медленный Tracker больше не вызывается под этими блокировками. Перед подготовкой,
claim и публикацией снимается актуальная проекция тикета; сетевой вызов находится
вне транзакции запроса. Затем под блокировками заново проверяются локальные права,
парк, скрытие задачи, настройки и состояние задания. Перед публикацией проекция
обновляется заново, поэтому изменение парка в Tracker во время inference не
обходится повторным использованием старого снимка. Сохраняется штатный TTL кэша
Tracker: это не обещание мгновенной свежести внешнего сервиса.

После исключения из tick worker снова включает восстановление прерванных
заданий на следующем разрешённом проходе. Это закрывает зависание `running`
после временной ошибки финального commit. Worker выполняет проходы последовательно
под эксклюзивной lease; восстановление не пересекается с ещё работающим проходом.
Задание становится `failed`, внешнее действие — `uncertain`, без автоматического
повтора. При успешных проходах дополнительные UPDATE восстановления не выполняются.

## Обучение

Раньше пачка событий обучалась вне административных блокировок. Воспроизведено
завершение изменения настроек и удаления знания при ещё выполняющейся пачке.
Теперь действует тот же порядок, что у импорта пакета: `ai-controls`, затем
`ai-knowledge`. Конфигурация перечитывается после ожидания; знания, планирование
правил, маркер обработки события и commit находятся внутри этого участка.

Регрессия с настоящим PostgreSQL advisory lock проверяет, что пачка после
ожидания видит выключенный ИИ и не создаёт знания/не завершает событие.
SQLite-проверки используют отдельные сессии и потоки, включая удаление знания.

## Очистка

Успешные тесты скриптов и черновики без разговора оставались в БД бессрочно:
очистка сбойных заданий их не выбирала, а история очищала только разговоры.
Теперь очистка истории старше выбранного срока удаляет также завершённые
задания без беседы вместе с вводом и результатами. Действующие скрипты, правила,
знания и квитанции внешних действий сохраняются.

Выбор старых неактивных бесед и удаление выполняются SQL-подзапросами без
материализации всех ID в Python и без ORM `RETURNING` синхронизации. Очистка
получает `ai-controls → ai-queue`, чтобы конкурентная отправка сообщения не
попала между отбором беседы и её удалением. Тест с реальными locks подтверждает,
что новая queued job, её сообщение и беседа сохраняются без orphan-записей.
SQL отдельно проверен на PostgreSQL с настоящими внешними ключами.

UI явно показывает срок 30 дней и отдельные количества удалённых бесед,
сообщений и заданий. Старый ответ API с одним `deleted` также обрабатывается.

## Удалённый устаревший путь

Удалён `prompts.system`: поиск по отслеживаемому Python-коду не обнаружил
вызовов или импортов этого helper. Он оставался от прежнего построения промпта
без ограничения контекста. Отправляемые сообщения по-прежнему создаёт
`fit_context`; его пять проверок прошли после удаления. Политика, токенизация,
бюджет контекста и формат источников не менялись.

## Полнота выдержки инструкции

В длинной инструкции выбранный второй фрагмент начинался недалеко от начала.
Выравнивание по локальному абзацу отбрасывало обязательные подготовительные
условия, хотя начало и весь выбранный фрагмент помещались в лимит 2 400 символов.
Теперь в таком случае сохраняется непрерывное начало, а обрезка по абзацу не
отсекает выбранный фрагмент. Для более удалённых фрагментов прежний формат
начала и выдержки с явным пропуском сохраняется.

Синтетический тест проверяет условие обесточивания и нужный шаг. На прежних
18 проверочных вопросах ожидаемый источник по-прежнему найден в 18 случаях,
нужное доказательство — в 18 вместо 17. Лимит выдержки, бюджет промпта и
публичный seed не менялись. Это набор разработки поиска, не независимая оценка
качества ответов Bonsai или аппаратная приёмка.

Эти примеры перенесены в публичный regression fixture без исходных путей,
приватной карты или ключа публикации. Новый тест использует весь поставляемый
JSONL и настоящий пакетный импорт/индекс, затем проверяет 18 запросов. Он прошёл
за 26,46 с. Дополнительно он прошёл за 26,56 с из отдельного `git archive`
коммита `1934270e`, содержащего только отслеживаемые `apps/api`, `deploy` и
`scripts`. Импорт Python-модулей проверен из этой копии; каталогов приватных
данных и `output` в ней нет. Использованы готовые зависимости локальной venv.
Текст корпуса и его
SHA256 не менялись. Для вопроса об инструменте закреплено полное «2,5 мм» вместо
прежнего слабого совпадения по одной цифре.
