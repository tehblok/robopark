# Robopark: аудит перед пересмотром продукта

Дата: 26.09.2026. База: незакоммиченное дерево `main`. Этот документ не является приёмкой релиза или свидетельством установленной версии.

## Границы и источники

- Полностью прочитан `docs/handoffs/2026-09-25-robopark-handoff.md`; перед анализом сняты `git status`, `git diff --stat` и изучены относящиеся к выводам изменения. В дереве на начало аудита было 73 изменённых отслеживаемых файла и несколько неизвестных файлов. Защищённые пользовательские файлы не редактировались.
- Изучены маршруты, роли, интерфейсные примитивы, auth/PWA, backend RBAC и park scope, host bridge, OTA и политика хранения. Это обзор архитектуры и рискованных контрактов, а не построчная экспертиза каждого файла.
- Живой сайт открыт под ролью владельца. Без изменения производственных данных проверены `/overview`, `/work`, карточка задачи и вкладка проверки, `/robots/:vin` и ошибки, `/inventory`, `/reports`, `/campaigns`, `/schedule`, `/analytics`, `/admin`, `/admin/emergency/config` и `/system`. Остальные роли, запись данных, телефон и установленная PWA этим проходом не проверялись. Попытку включить мобильный viewport остановила ошибка автоматической проверки доступа к browser-инструменту (401); ограничение не связано с результатом проверки сайта.
- Доступа к установленному хосту и его коротким логам нет. Источник пропавших гигабайт и причина отсутствия host-метрик пока неизвестны.

**Отозванная гипотеза:** интервалы doctor 15 минут и TTL operation capabilities 5 минут сами по себе не создают разрыв. Снимок разрешённых операций публикует watchdog каждые 2 минуты (`cli.py`, `robopark-watchdog.timer`); doctor публикует другой, аппаратный профиль. Требуется диагностика хоста, прежде чем приписывать ему ошибку экрана «Система».

## Что видно в установленной версии

- `/campaigns` показывает «Сервис временно недоступен» при загрузке списка. В локальном дереве уже исправлен PostgreSQL `DISTINCT/ORDER BY` и добавлен целевой тест (`services/campaigns.py`, `test_campaigns.py`); на сайте эти изменения ещё не установлены. Без серверного лога нельзя утверждать, что это единственная причина текущей ошибки.
- `/system` показывает устаревшие метрики и «Нет данных» почти во всех категориях. Локальный интерфейс уже различает HTTP/bridge/worker ошибки (`SystemPage.tsx`, `SystemMetrics.tsx`, `worker_healthcheck.py`), но установленная версия этого не отражает. Первопричина отсутствия телеметрии без host-логов не установлена.
- В меню «Ещё» виден тёмно-синий внешний прямоугольник. Локальный diff общего примитива диалога меняет фон на нейтральную поверхность (`design-system/overlays/overlays.css`); на сайте правка ещё не установлена.
- Карточки задачи и робота открываются. У робота 1427 три события выводятся как неизвестные диагностические ошибки; в редакторе показаний каталог пуст. Это подтверждённый пробел настройки/данных на сайте, но происхождение пустого каталога без хоста неизвестно. Вкладка проверки задачи 381655 открылась на схеме без настроенных показаний. Действия, меняющие данные, не выполнялись.
- `/overview`, `/inventory`, `/reports`, `/schedule`, `/analytics`, `/admin` загрузились под владельцем. Факт открытия страницы не подтверждает все формы, права и рабочие сценарии.

## Что уже подготовлено в рабочем дереве до этого аудита

Локально присутствуют исправления старой PWA с безопасной активацией и перезагрузкой клиента, TOTP владельца с QR/ручным ключом и recovery-кодами, ошибка кампаний, типизированный worker healthcheck, различимые состояния System, общие spacing/radius/color tokens и ограничение хранения OTA/BuildKit/release. Также есть тесты последовательных OTA, отказа/прерывания и rollback. Их нужно оценивать на точном source hash перед выпуском; исторические PASS из `docs/product-completion` относятся к прежним деревьям.

## Рекомендуемая переработка

| Подход | Что даёт | Цена |
| --- | --- | --- |
| Поэтапно укрепить текущую классическую систему — рекомендуется | Быстро закрывает найденные дефекты, сохраняет offline/PWA, данные и rollback | Потребует последовательно привести старые экраны и контракты к общим примитивам |
| Пересобрать frontend поверх существующего API | Больше свободы для новой навигации и компонентов | Временное сосуществование двух UI, повторная проверка всех ролей и PWA-сценариев |
| Переписать frontend, API и OTA одновременно | Можно навязать единую схему с нуля | Высокий риск потерять уже реализованные права, интеграцию Tracker, миграции и восстановление |

Предлагаю первый подход. После проверки настоящих рабочих сценариев можно решить, какие разделы менять сильнее; сейчас данных для полной переписи нет.

1. **Сначала целостность и безопасность:** закрыть park/RBAC утечки; устранить нехватку места до OTA; оставить fail-closed host bridge и безопасный rollback. Эти задачи не требуют новой темы или переделки всех экранов.
2. **Затем классическая дизайн-система:** одна сетка и отступы страницы/панели/карточки, один набор цветов и радиусов, читаемые состояния loading/error/empty/stale, доступные зоны на телефоне, меню без выделяющегося внешнего блока. Проверять общий примитив на desktop и mobile для каждой роли, затем ключевые вложенные состояния. «Новый A» не возвращать.
3. **После этого уточнить продуктовую логику:** явная модель состояний задачи (Tracker, локальная очередь, синхронизация, проверка/закрытие), понятные переходы и ошибки для механика/оператора; для диагностики — управляемый каталог правил и показаний с источником данных и качеством сопоставления. Новые поля БД вводить только после проверки требуемых инвариантов, миграций и обратной совместимости.
4. **Схема эксплуатации:** для System публиковать типизированные агрегаты диска и причины недоступности; для OTA добавить обязательный бюджет места; сохранять current+rollback и нужный кандидат, не касаться Docker volumes/PostgreSQL и чужих ресурсов. Сначала измерить реальный хост, затем решать, нужна ли замена локальной BuildKit сборки на другой формат доставки.

Полная перепись системы сейчас увеличит риск потери уже работающих PWA/offline, RBAC, Tracker workflow и rollback-контрактов. Рекомендуемый путь — укреплять эти контракты и поэтапно упрощать web и backend модули с проверяемыми сценариями.

## Критерии перед OTA

- Короткие регрессии для доступа между парками, overrides, login → рабочий экран со старым service worker, TOTP setup/recovery, двух последовательных OTA, неуспеха/прерывания и rollback.
- Целевые desktop/mobile geometry и сценарии основных ролей; отдельная проверка реальной установленной PWA и host bridge после обновления.
- Read-only измерения хоста: OTA uploads/cache, releases/snapshots, `docker system df -v`, BuildKit, PostgreSQL volumes, journald, backups/diagnostics. Любое реальное удаление — только после точного preview и отдельного разрешения.
- Для точного финального дерева отдельно согласовать долгие release gates. До них не объявлять релиз production-ready. Не коммитить и не собирать OTA без явного запроса.
