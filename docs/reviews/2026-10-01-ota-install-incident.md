# Сбой установки OTA 0.2.0

Операция `02034dc6-bf16-447c-aeb3-a1ae309ef62f` завершилась
`host_operation_failed` 1 октября 2026 года. Причина самого сбоя OTA пока не
установлена. Повторная установка не выполнялась.

При последней проверке хост оставался на
`0.2.0-rc.16.dev11074319897666147461`, build `60b6847fba6085bc`,
с БД `0054_park_coordinates`. Интерфейс показывал работающие сервисы и пустую
очередь. Это наблюдение состояния после ошибки, а не доказательство успешного
обновления или отсутствия остальных дефектов.

## Подтверждённые дефекты и локальные исправления

1. Ответ `401 invalid_credentials` от проверки пароля/TOTP вызывал глобальный
   сброс сессии. Только для `/admin/privileged-auth/reauthorize` этот ответ
   теперь сохраняет текущую сессию и передаёт ошибку форме. Настоящий
   `401 Unauthorized` по-прежнему вызывает выход. Точная причина отклонения
   подтверждения на действующем сайте не зафиксирована.
2. API скрывал безопасные коды отдельных этапов OTA за `host_operation_failed`.
   Теперь разрешённый код из файла состояния передаётся только при строгой
   схеме версии 1, совпадающем ID операции и терминальном состоянии ошибки.
   Неизвестные строки по-прежнему заменяются общей ошибкой.
3. Диагностический архив включал только старые файлы обновления. Добавлены
   ограниченные проекции `ota-update-journal.json` и `ota-status.json`:
   ID операции, версия, этап и разрешённый код ошибки. Исходные stderr,
   вложенные данные запроса и секреты не включаются. Чтение ограничено 64 КиБ,
   обычным файлом и запретом следования по символьной ссылке.
4. При проверке новой обработки воспроизведены и исправлены сбои на массивах
   и объектах вместо строк `phase`/`error`. Независимое ревью также обнаружило
   пропущенный штатный код `ota_unsafe_current`; он добавлен в оба списка.

Эти изменения находятся только в рабочем дереве. Установочный пакет с SHA256
`9e9f1534a6ed18e9e768f00bee107c0a4fb76b509f12216bc07b85aeb7c2bc93`
их не содержит. Формат hash-only OTA v1 и механизм обновления не менялись.

## Отсутствующий журнал

Отсутствие `/var/log/robopark/ota-update.log` само по себе не устанавливает
причину и не доказывает удаление файла после перезагрузки. В текущем
`SystemRunner` проверки готовности используют `run_cleanup`, который временно
отключает запись этого журнала. Кроме того, запись не создаётся для пустого
вывода команды. Поэтому некоторые ошибки могут завершиться без этого файла.

У пользователя есть только терминал хоста. Запрошен безопасно отфильтрованный
вывод трёх файлов под `/var/lib/robopark/ops/`:

- `state/ota-update-journal.json`;
- `state/ota-update-receipts/02034dc6-bf16-447c-aeb3-a1ae309ef62f.json`;
- `public/ota-status.json`.

Этот вывод пока не получен. Этап сбоя, состояние receipt и условия конкретного
хоста остаются неизвестными. Продолжительность операции около пяти минут
не считается доказательством таймаута или иной причины.

## Диагностика через сайт после потери доступа к терминалу

Пользователь подтвердил штатную операцию кодом TOTP. Операция
`46d94952-7022-40bf-8e94-6bc3c498e6e3` завершилась успешно
`2026-10-01T19:24:02.727859Z`; архив скачан и проверен. SHA256:
`60d6090f8c7487774cf6a0251e2055ffe26fff29434992476bc7f71ea9abe671`.
Архив сохранён в каталоге инцидента как
`robopark-diagnostics-46d94952-7022-40bf-8e94-6bc3c498e6e3.zip`.

В отчёте 30 проверок: 29 успешных и одна ошибка `storage_retention`.
Все четыре контейнера (API, PostgreSQL, web, worker) имеют состояние healthy.
Проверки DNS, HTTPS, часов, конфигурации, миграций, отката и текущего релиза прошли.
Версия осталась rc.16 с БД 0054. Эти проверки подтверждают текущее состояние,
но не восстанавливают условия неудачной установки в 10:59 UTC.

`update-status.json` содержит только старый `current_healthy` от предыдущего
обновления; typed OTA journal/status в архиве отсутствуют. Экспортированные
журналы systemd содержат только метаданные событий после 15:00 UTC, без текста
команд и без записи неудачной операции. Причина сбоя OTA всё ещё неизвестна.

Для `storage_retention` показано `категория none`. Дополнительный read-only
запрос `/api/admin/system/summary` дал `last_cleanup.blocked=true`,
`pressure=false`, пустые значения floor/reclaimed и отсутствие дискового
давления. Эта форма соответствует ветке `HostBusy` в `retain_storage()`;
обычная ветка сканирования заполняет floor/reclaimed числовыми значениями.
При `HostBusy` очистка не выполняется. Точного владельца host lock API
не публикует. В исследованном doctor/diagnostics пути вложенного захвата
собственного lock не найдено.

Обнаружен отдельный дефект представления состояния: `busy=true` сохраняется
в приватном отчёте, но теряется в публичной проекции. Doctor и API классифицируют
`blocked=true` как ошибку; интерфейс выводит «Очистка: ошибка». Исправление
этого дефекта выполнено локально, отдельно от неизвестной причины OTA.

Следующий плановый запуск очистки в 19:30:50 UTC завершился без блокировки.
В read-only снимке сайта от 19:33:39 UTC поля `cleanup_failed=false`,
`blocked=false`, `pressure=false`; worker работает. Снимок сохранён в
`cleanup-next-cycle.json`. На хосте для этого не выполнялись дополнительные
очистки, перезапуски или установки. Наблюдение подтверждает временный характер
блокировки.

Признак отложенной очистки теперь передаётся от хоста через API до обоих
интерфейсов состояния. Только настоящий boolean `true` подавляет ложную
классификацию ошибки. Нехватка места и ошибки хоста/API сохраняют приоритет.
Старый payload без признака `busy` совместим. Дополнительно исправлено
противоречивое сообщение при одновременных busy и текущем дефиците места:
панель больше не утверждает, что отложенная очистка завершилась.

Проверки этого изменения: host profile 67 passed, API profile 19 passed,
окончательный web profile 90 passed; TypeScript, oxlint, API Ruff и
`git diff --check` прошли. Обычный host Ruff сообщает шесть существующих
BLE001 в незатронутых обработчиках `doctor.py`; проверка с исключением
этого правила прошла. Независимое ревью закрыто после исправления смешанного
сценария busy + дефицит места.

Первичные RED-запуски host/API не дошли до assertions из-за окружения;
они не считаются доказательством TDD. Последующая проверка в отдельной копии
кода с отключёнными изменениями дала две ожидаемые ошибки host и одну API;
те же проверки на рабочем коде прошли. Для смешанного UI-сценария сохранён
полный RED → GREEN. Подробные результаты и хэши файлов:
`retention-busy-verification.json` в каталоге инцидента.

Новые исправления не собраны в OTA и не установлены на production. Причина
исходного сбоя установки остаётся неизвестной; для продолжения нужен доступ
к сохранённому typed journal/receipt/status на хосте.
