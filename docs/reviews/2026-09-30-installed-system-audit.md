# Повторный аудит Robopark

Дата: 30.09.2026. Источник кода: текущее незакоммиченное дерево `main`. Проверенный сайт: https://robopark.ru.tuna.am. Результат этого прохода — локальные исправления и проверка выбранных сценариев. Установленный хост не обновлялся; этот документ не подтверждает готовность всей системы к production.

До отдельного запроса упаковки OTA и архив не создавались; упаковка описана в дополнении ниже. Коммит не выполнялся. Данные, настройки, роли и тикеты установленной системы не менялись; очистка на реальном хосте не выполнялась.

Внешняя база знаний и межсессионная память Стефании через профильные skills/tools в этой сессии недоступны. Контекст восстановлен из разговора, handoff и документов репозитория, затем сверен с текущим кодом и сайтом.

## Исправления этого прохода

### SLA при позднем назначении парка

`tracker_history.py`: если в момент первого перехода в очередь парк отсутствовал, выбирается первый однозначный парк из подтверждённой истории последующих изменений тегов. Начало SLA остаётся временем первого перехода, а не временем назначения парка. Последующий перенос, повторное открытие и изменение часового пояса парка не сбрасывают исходный срок. Неоднозначная или повреждённая история сохраняет неизвестный SLA; время создания тикета не подставляется.

Падающий тест воспроизвёл отсутствие anchor_timezone. Исправление проверено на рабочем окне 09:00–21:00, пятичасовом SLA, календарном простое, переносе и reopening. На установленном сайте изменения ещё отсутствуют. Для конкретного тикета эффект зависит от наличия подтверждённого изменения тегов в Tracker.

### BuildKit preview и cleanup

`storage_inventory.py`, `builder_cleanup.py`: общий ограниченный парсер принимает действительные SI/IEC размеры и числовые строки, отвергает bool, отрицательные, повреждённые и чрезмерные значения. Preview и ручная очистка больше не расходятся по формату размера. Сохраняются проверки владельца builder, приватной записи и точного ID. Проверено на fake runner, без реального prune.

### Старый клиент PWA

`sw-template.js`: явная кнопка обновления исторического клиента теперь может подтвердить только свою молчащую WindowClient. Другие вкладки обязаны подтвердить безопасное состояние; отрицательный ответ/veto и незавершённые действия/фото блокируют обновление. Состояние IndexedDB проверяется повторно перед активацией.

Автоматическое обновление молчащего старого клиента сознательно не подтверждено: он не сообщает о несохранённой форме в памяти. Полностью автоматический переход без этого знания опасен. Для такого клиента остаётся однократная явная кнопка обновления; после перехода вход сразу открывает рабочий экран без ручного refresh. Старые тесты, обещавшие автоматическую активацию молчащего клиента, приведены к этому безопасному контракту; первоначальное падение сохранено как факт аудита, а не выдано за PASS.

### Общие отступы списка и деталей

`MasterDetail.css`: обе колонки используют вертикальную сетку с общим `--rp-form-gap` и выравниванием к началу. Ранее список мог передавать fragment из нескольких блоков, между которыми получался промежуток 0 px. Новая геометрическая регрессия на 390/1440 px сначала упала с 0, затем прошла. Скриншоты после изменения просмотрены. Проверены также потребители: карточка задачи, репорты, пользователи и тёмная тема на ПК.

`IssueActionsPanel.test.tsx`: исправлено чтение всех совпадающих media-блоков вместо только первого. Продуктовый CSS этим изменением не менялся.

### Восстановление OTA

`ota_update.py`: abort_snapshot и rollback проверяют готовность бота, если он включён. Подготовленный кандидат получает строгую ограниченную квитанцию до переименования каталога; cleanup сохраняет current/previous/recovery и не доверяет symlink или изменённой квитанции. Пути нормализованы перед сравнением защищённых релизов.

Файлы, manifest и вложенные каталоги синхронизируются до публикации кандидата; каталог state — после записи квитанции, родитель релизов — после rename. Это закрывает выявленные окна потери записи и оставленного кандидата при прерывании. Проверки работают на временной файловой системе и fake runner. Физическое отключение ARM-хоста не выполнялось. Независимое ревью финального OTA diff не нашло оставшихся воспроизводимых дефектов в этой области; это не является ревью всех модулей системы.

## Что остаётся до безопасного выпуска

1. **Восемь недоступных host actions не являются завершёнными функциями.** Rollback, обновление пакета, restart сервиса, reboot, создание/восстановление backup и форматирование USB имеют недоступные production adapters; verify backup требует отдельного безопасного recovery context. Кнопки нельзя просто включить. Требуется отдельная реализация и проверка preview/контекста/защиты для каждого действия.
2. **Чистая установка после прерывания не имеет полного resume.** Повторная попытка может упереться в empty-host guard. Требуется восстановление установки без вынужденного удаления данных; это известный открытый пункт плана базовой системы.
3. **Исправления ещё не установлены.** Нужно сформировать отдельно разрешённый пакет, затем проверить на ARM хосте readiness, автозапуск, host bridge, SLA и private BuildKit inventory. Текущий сайт показывает прежнюю версию.
4. **Android PWA и реальный Wi-Fi не проверены физически.** Desktop Chromium с настоящим service worker проверяет браузерный протокол, но не заменяет установку на телефон, камеру, работу в фоне, холодный старт и восстановление сети.
5. **Совместный production workflow всех ролей не принят.** Пока нет механиков, оператора и смен на хосте. Повторная неисправность с реальными закрытыми задачами, комментарии/фото в живом Tracker и параллельные PostgreSQL claims требуют отдельного контролируемого прохода.
6. **Импорт существующего Telegram-бота ещё не выполнен.** На сайте бот выключен. Локальные API/lifecycle тесты не подтверждают сохранность конкретного экспортированного ZIP и внешнюю доставку Telegram.
7. **Производительность под множеством пользователей не измерена.** Сохраняются локальные кэши и пакетная синхронизация, их целевые регрессии прошли. Нагрузочные числа без отдельно разрешённого теста не заявляются.

Следующий обязательный этап — закрыть production adapters и install resume, затем провести принятие на точном собранном пакете и реальных устройствах. До этого утверждать «всё готово» оснований нет.

## Дополнение: офлайн-сессия, кэш и изменения интерфейса

### Что исправлено локально

- **Офлайн-сессия.** После сетевой ошибки, timeout, временного 5xx или некорректного ответа прокси приложение восстанавливает последнюю подтверждённую учётную запись и доступные парки. Для этого сохраняются только ограниченные метаданные интерфейса, без пароля, cookie и токенов. Срок — 72 часа от последней успешной серверной проверки; офлайн-чтение его не продлевает. Первый вход требует сети. Выход и подтверждённый сервером 401 удаляют локальную идентичность. Отказ 403 отдельному ресурсу очищает защищённые данные этого клиента, но не выдаётся за отзыв всей сессии.
- **Повторная проверка и смена аккаунта.** После восстановления сети выполняется `/me`. Смена аккаунта в другой вкладке немедленно приостанавливает локальный доступ к кэшу; новая учётная запись принимается только после серверной проверки. Очередь активации кэша закрывает гонку A → B → A. Новый явный вход очищает ранее сохранённые ресурсы даже при совпадающем ID аккаунта после переустановки сервера.
- **Явный выход офлайн.** Отдельный воспроизводящий тест показал автоматический повторный вход при возвращении сети: недоставленный logout оставлял серверную cookie действующей. Локальная запись о выходе теперь блокирует bootstrap `/me` до нового успешного входа. Для завершения прерванной очистки она хранит только account ID и дескрипторы областей локальных черновиков, без credentials, содержимого фото или текста задач. Поздний ответ старого logout не снимает этот флаг у нового входа. Если браузер полностью запретил локальное хранение, устойчивость этого флага между перезапусками недоступна; активное состояние очищается в памяти.
- **Верхний индикатор.** Офлайн-сессия остаётся серой даже при `navigator.onLine=true`, если до сервера нет связи. Это воспроизведено в настоящем service worker сценарии. В таком состоянии установка PWA-обновления блокируется до проверки идентичности и безопасного состояния очереди.
- **Активация после выхода.** Локальный флаг выхода при следующем bootstrap доводит прерванную очистку и объявляет интерфейс анонимным после её завершения. Это устраняет найденную ревью вечную блокировку waiting service worker на экране входа. Отдельные тесты проверяют очищенные ресурсы, положительный safe activation ответ и восстановление очистки после удаления offline identity: привязанное share-фото удаляется, фото репорта помещается в карантин, ещё не привязанное фото сохраняется. Верхний индикатор на ПК также исправлен: ширина прежней пустой рамки была 556 px; теперь применяется компактный размер элемента управления.
- **Возврат на экран.** Переключение выбранного парка больше не уничтожает весь кэш аккаунта. Ресурсы разделены по ключам парка и правам пользователя; сохранённый экран рисуется сразу, затем обновляется. Изменение доступов очищает защищённые снимки. Поздние ответы закрытого экрана не подменяют новую очередь.
- **Акцент.** В меню «Ещё» доступны оливковый, синий, фиолетовый и тёплый акценты. Настройка личная для устройства, применяется до первого React paint и работает отдельно от светлой/тёмной/системной темы. Основные поверхности и текст нейтральные.
- **График.** Поддержаны 5/2, 4/4, 3/3 и 2/2, первый день смены и конечная дата периода. Отпуск/болезнь обратимо подавляют пересекающиеся смены, не удаляя исходные записи и не сдвигая дальнейший цикл. Отсутствующий оператор не считается доступным по графику.
- **Карточка и SLA.** Кнопка «Свернуть» удалена. Основные показатели очереди и обзора — обратный SLA 5:00 → 0:00, только при подтверждённых начале очереди и часовом поясе. ## Дополнение: доступ механика, общий SLA и обслуживание хоста

### Подтверждённые причины

- На установленном сайте парк имел тег `АрмаМск`, а задача — `АрмаМСК`.
  Tracker сопоставлял их без учёта регистра, но локальный ACL — строго.
  Это убирало задачи у механика, хотя владелец видел их. Такое же сравнение
  влияло на обзор, аналитику и привязку часового пояса SLA.
- Чтение проверки робота ошибочно требовало claim задачи. Это запрещало
  механику диагностировать робота из доступной задачи другого открытого статуса.
- В списке история SLA оставалась в кратком process cache, обзор не запрашивал
  отсутствующие якоря. Полный worker-обход был раз в два часа и брал две истории.
- Старые типизированные System commands не давали владельцу сохраняемый результат
  и точную ссылку для скачивания диагностики. Восемь адаптеров отсутствовали.
- В опубликованном ранее состоянии Buildx присылал текстовый `Size`, например
  `8.192kB`; собственный builder существовал, но его инвентаризация была заблокирована.

### Исправления в рабочем дереве

- Единое Unicode casefold-сопоставление тегов для ACL, диагностики, обзора,
  аналитики и исторического парка. Доступ остаётся ограничен назначенным парком;
  read-only диагностика не требует claim, мутации сохраняют проверку владения.
- Пустая очередь предлагает «Показать все открытые задачи». Карточка показывает
  реальный статус Tracker. Ожидающее списание по-прежнему блокирует дублирование,
  хотя обычная подпись синхронизации удалена по требованию пользователя.
- Список, обзор и детали используют общий подтверждённый SLA-якорь. История
  сохраняется в базе и не запрашивается заново для уже известного начала/пояса.
  Лёгкий worker дозаполняет максимум две истории с интервалом 15 секунд;
  полный обход сохраняет прежнюю частоту. Расчёт 5:00 → 0:00 остаётся локальным.
- Устранены гонки общей history-state между API и analytics: atomic upsert,
  стабильный порядок PostgreSQL locks, блокировка одной истории при ingest,
  `NULLS FIRST`. Кэш changelog учитывает версию тикета. Старый отрицательный
  результат перепроверяется через две минуты, отказ доступа — через сутки;
  первый подтверждённый переход и часовой пояс при reopen не сбрасываются.
- Реализованы конечные адаптеры пакетов/служб, reboot, rollback, USB и backup.
  UI получает доверенный boot/TTL context, показывает последние 20 операций
  и точную ссылку «Скачать диагностику». Старые общие download routes закрыты,
  чужой результат не подменяется.
- Snapshot для USB backup выполняется как дочерняя операция и не конфликтует
  с активным parent job. Reboot после смены boot ID не повторяется вслепую.
  Ключ backup создаётся установщиком; предусмотрены защищённые export/import
  для восстановления после переустановки. Предел снимка совпадает с restore.
- Парсер BuildKit принимает строковые размеры; ограничение собственного кэша
  после успешной сборки проверяет результат. Широкая очистка Docker/volumes
  и удаление PostgreSQL не добавлялись.
  Дополнительно воспроизведён и исправлен отказ на JSON-отчёте из 203 записей:
  прежний предел 64 КиБ противоречил разрешённым 1024 записям. Для собственного
  du/preview установлен отдельный предел 2 МиБ; проверка идентичности builder
  остаётся 64 КиБ. Два теста сначала упали, затем целевые 50 тестов прошли.

### Повторная остановка Tuna после веб-обновления

В архиве rc.10 `SystemOtaUpdateRuntime.resume` не восстанавливает ingress.
Веб-обновление выполняется уже запущенным updater прежнего релиза, поэтому
новый код его финализации не участвует в первом переключении. Запасной
запуск из нового OTA launcher работал только для `UPDATE.sh`.
`robopark.service` теперь имеет post-start через новый доверенный launcher:
только явно включённая Tuna запускается `systemctl start --no-block`, чтобы
не ждать зависимость `After=robopark.service` внутри самого старта приложения.
Синхронная финализация использует idempotent start вместо restart.
Ключи и домен не читаются; disabled/masked не включаются. Недоступность
туннеля не останавливает локальный кабинет; существующая диагностика
показывает её отдельно. Тесты включают изолированный процесс новой
активированной unit и настоящий SystemRunner с контролируемым systemctl.
Это проверка интеграционного контракта; настоящий Linux systemd на ARM
и факт причины на конкретном хосте остаются непроверенными без его лога.

На сайте подтверждены завершённая OTA-операция и rollback release
`0.2.0-rc.10.dev13230504077521760833`, что согласуется с найденным путём
старого updater. После ручного запуска владельцем сайт и Tuna доступны.
168 целевых host tests прошли за 10,19 с, 12 web OTA tests также прошли.
Точный rc.14 отдельно проверен Python и API verifier, checksum inventory,
367 Python sources parsed и наличие нового post-start в архиве.
Контракт ordering проверен по [systemd.service](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml)
и [systemctl](https://github.com/systemd/systemd/blob/main/man/systemctl.xml).
