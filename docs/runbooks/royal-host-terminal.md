# Терминал хоста для royal

Терминал открывается отдельной страницей из «Система». Доступен только активному royal с настроенным TOTP и действующей сессией сайта. Для каждой новой сессии нужны пароль и свежий TOTP; код восстановления для открытия терминала не подходит. Пароль/TOTP не сохраняются в форме после отправки.

По умолчанию shell работает как `robopark-maint`: домашний каталог `/var/lib/robopark/terminal-home`, без sudo, Docker, группы API и Linux capabilities. Файлы пользователя можно создавать и редактировать обычными установленными средствами Linux. Root открывается отдельно и даёт полный контроль над хостом. Этот профиль не является sandbox: сделанные изменения остаются после закрытия; отдельные службы, намеренно созданные root, могут пережить сессию.

## Завершение и ограничения

| Условие | Предел |
| --- | --- |
| Обычная сессия | 60 минут |
| Root | 15 минут, абсолютный предел |
| Нет ввода | 10 минут; output/heartbeat не продлевает срок |
| Обрыв соединения | 15 секунд на переподключение |
| Потеря API/lease | 20 секунд, затем завершение worker |
| Остановка systemd worker | SIGTERM, затем SIGKILL всей cgroup через 5 секунд |
| Одновременные сессии | 2 на хост: одна обычная и одна root |

Выход из аккаунта, изменение пароля/прав, отзыв входа или замена TOTP отзывают терминальные сессии. API перепроверяет доступ не реже чем каждые 5 секунд. Браузер не повторяет введённые команды после reconnect. Старый экран очищается при смене доступа. Ctrl+C передаётся в PTY; многострочная вставка требует подтверждения. Буфер вывода ограничен; переполнение завершает сессию.

## Обновление и восстановление

Проверенный путь со старого runtime: `rc.16.dev11074319897666147461` → foundation `rc.17.dev16437318597787721811` → пакет терминала. Feature-пакет совместим только с этой foundation. Формат OTA v1 с SHA-256 сохранён, подпись издателя не добавлена.

Foundation исправляет bootstrap: первую ступень собирают с PostgreSQL 17.6, новый runtime перед следующей сборкой получает требуемый образ БД; отдельный Alembic engine выполняет миграции при включённом maintenance, обычные записи приложения остаются заблокированы. Все ранее выпущенные миграции сохранены. Новая миграция `0056_host_terminal` добавляет только данные управления терминалом.

Перед обслуживанием завершите сессии терминала. Штатный UI возвращает `terminal_active`, если активные сессии известны. Если запрос обслуживания успел попасть в очередь одновременно с подключением, broker завершает сессии с причиной `host_operation_requested`, освобождая host lock. Прямой updater сначала останавливает broker/workers, затем получает lock. Кандидат миграции/smoke не получает терминальный сокет. Только основной API имеет read-only bind каталога сокета.

Rollback останавливает сессии, возвращает snapshot БД/config/units. При откате на foundation терминальные units и mount отсутствуют; старые tickets и epoch недействительны. В случае сбоя настройки терминала основной сайт продолжает работать, capability сообщает недоступность.

Ручные правки внутри `/opt/robopark/current` не являются постоянной конфигурацией: они могут нарушить проверки целостности и будут заменены OTA. Исправления продукта вносите в исходники и доставляйте новым пакетом; для поддерживаемых настроек используйте интерфейс/host configuration. Не редактируйте выпущенные миграции.

Терминал доступен, только пока работают сайт, API, брокер и туннель. Восстановить полностью недоступный сайт через него нельзя; сохраните резервный физический/SSH-доступ, если такой доступ возможен.

## Граница доверия и диагностика

Брокер слушает только Unix socket; новые TCP/SSH listeners не открываются. Клиентский socket допускает UID 10001 API. Worker socket отдельно проверяет Unix UID и точный MainPID admitted systemd unit. Полный захват API остаётся возможностью делегировать root: терминал не защищает хост от полного RCE в доверенном API.

При каждом setup код worker собирается из установленного релиза в `/run/robopark-terminal-workers/worker.pyz`, владелец root, группа robopark-maint, права 0440. Включены только модули worker/protocol/setup и фиксированный entrypoint. Обычный пользователь не получает доступ к закрытому дереву релиза, конфигурации или приватному состоянию. При загрузке хоста runtime создаётся заново; обновление останавливает setup и заменяет runtime до запуска broker.

Системная служба setup использует стандартного пользователя root без явного `User=root`. В systemd 255 сочетание явного `User=root`, seccomp-настроек и `NoNewPrivileges` может лишить процесс `CAP_SETUID`, необходимого для проверки worker через `runuser`. Проверка запуска от Linux root остаётся в коде setup; ограничения службы и профиль обычного worker сохраняются. Контракт описан в [документации systemd](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#User=).

Начиная с корректирующего пакета после rc.19, первый сбой дочерней команды setup сохраняет до 2 МиБ вывода в `/var/log/robopark/terminal-setup.log` с правами 0600. Это журнал фиксированных команд подготовки, отдельный от интерактивных сессий. При анализе сопоставляйте время файла с запуском службы: успешный запуск не стирает предыдущую ошибку. Сырой файл не публикуется в API или диагностическом ZIP.

В постоянном журнале сохраняются lifecycle, профиль, идентификаторы, причина завершения и счётчики байтов; команды, ввод и output не записываются. Private state содержит связку владельца/сессии входа, доступную только root. Диагностический ZIP экспортирует максимум 20 записей из строгого списка безопасных полей. Host history ограничена 30 днями; после безопасной ротации без живых сессий или перезапуска сохраняются 2048 последних завершений. При высоком churn записи могут удаляться раньше. При 3072 записях и отсутствии живых сессий broker публикует новый epoch/revision, затем оставляет в памяти 2048 последних статусов и причин завершения. Старые create descriptor после этой границы не принимаются. Живая maintenance или root-сессия откладывает ротацию, поэтому дисковая история и registry в памяти могут вырасти до жёсткого лимита 4096; новые сессии остаются закрыты до её завершения и успешной публикации новой границы. Уже выданное подтверждение TOTP, связанное с прежней revision, после ротации нужно запросить повторно.

Tuna inspector отключён через `TUNA_INSPECT=false` и `--inspect=false`, чтобы не сохранять HTTP-заголовки с cookie/формы подтверждения. HTTPS redirect сохранён. Параметры описаны в [документации Tuna](https://tuna.am/docs/tunnels/http/inspect/).

## Проверка релиза

Локальные unit/API/web тесты не заменяют Linux/systemd и live WSS. `scripts/terminal_acceptance.py` запускают только внутри выделенной disposable Linux VM с PID1 systemd и root-owned marker `/run/robopark-terminal-test-vm`. Результаты и точные версии пакетов находятся в `docs/reviews/2026-10-02-royal-terminal.md` и `output/audit/2026-10-02/royal-terminal/`. Статусы BUILT / TESTED / INSTALLED различаются; восьмичасовой тест не проводится.

Если royal видит `terminal_unavailable`, одного активного host broker недостаточно: API-контейнер должен получать `TERMINAL_BROKER_SOCKET=/run/robopark-terminal/broker.sock` и read-only bind каталога `/run/robopark-terminal` с `create_host_path=false`. Другим сервисам этот сокет не предоставляется.

Исправленный updater определяет terminal payload в staging, сохраняя final release paths в Compose. Для обновления со старого rc.18 boot preflight после restore recovery дополняет только API в доверенном pinned current Compose. Конфликтующая конфигурация блокирует старт, чтобы OTA мог штатно откатиться. Foundation без terminal payload остаётся совместимым.

Короткая проверка в изолированной Linux VM: `scripts/terminal_acceptance.py --mode api-boundary --output <path>`. Она проверяет контейнер API → BrokerClient → PTY после авторизации. Она не заменяет проверку входа, TOTP и WebSocket в браузере и не повторяет полный root900.

Для изменений setup обязателен отдельный gate на Ubuntu 24/systemd 255: `tests/terminal_linux/systemd_setup_probe.py --baseline-ota <исходный-rc19.ota> --candidate-ota <кандидат.ota> --output <отчёт.json>`. Запускайте его через `sudo python3` только в выделенной disposable VM с указанным выше marker, принадлежащим root и имеющим права 0600: проверка заменяет служебные пути и unit внутри VM. Она запускает unit и helper из обоих OTA, воспроизводит отказ исходного rc.19 без CAP_SETUID и требует успешной подготовки кандидата с теми же ограничениями systemd. Инструкция и сохранённый результат находятся в `output/audit/2026-10-03/royal-terminal-capabilities/README.md`. Проверка на systemd 249 не заменяет этот gate.
