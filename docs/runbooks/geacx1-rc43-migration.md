# RC43 → GEACX1: подготовка и перенос

Проверено по исходникам 13 октября 2026. Базовая поставка остаётся
**v0.2.0-rc.43**. Комплект подготовки не меняет опубликованный `.ota` и не
является новым релизом. Проверки на физическом AGX пока не выполнены.

Дополнительно подготовлен [модуль TensorRT/DLA/JPEG и сменных моделей](agx-acceleration.md).
Он поставляется отдельным companion и не меняет содержимое оригинального RC43.

## Что известно о плате

Источник: [geacx1-recovery-validation](https://github.com/tehblok/geacx1-recovery-validation/tree/7611b523e3311ba08d821449236736590ec23e35),
в частности [POSTCHECK.sh](https://github.com/tehblok/geacx1-recovery-validation/blob/7611b523e3311ba08d821449236736590ec23e35/recovery/POSTCHECK.sh).

| Компонент | Ожидаемый контракт комплекта восстановления |
|---|---|
| Модуль | AGX Orin 32 ГБ, P3701-0004, Tegra234 |
| Carrier | GEACX1 / 510JX0 r3.0 |
| ОС | Ubuntu 24.04, ARM64 |
| BSP | JetPack 7.2 / L4T R39.2.0 |
| Ядро | vendor `6.8.12-1021-tegra` |
| Охлаждение | `rb-jetson-service-fan.service` и vendor fan GPIO |
| CUDA/cuDNN/TensorRT | В recovery-образ не входят; проверяются на целевом хосте |

Это ожидаемые значения из репозитория, не снятые показания устройства.
`POSTCHECK.sh` дополнительно проверяет vendor-маркер carrier в DTB и модули
ядра. Запустить его из доверенной копии recovery-комплекта перед подготовкой.
Сам recovery-мастер при этом запускать не требуется.

## Комплект подготовки

Архив `robopark-agx-rc43-preparation.zip` содержит:

- самостоятельный `robopark-agx.py` (только стандартная библиотека Python);
- оригинальный `robopark-0.2.0-rc.43.ota`, загруженный из GitHub Release;
- эту инструкцию и руководства по NVMe, ИИ, производительности и recovery;
- `SHA256SUMS` и описание происхождения файлов.

Он не содержит резервной копии пользователя, секретов, firmware или весов модели.
В исходниках тот же диагностический модуль находится в
`deploy/host/robopark_host/agx_preflight.py`. Новая команда host-tools `agx-check`
и исправление информационного обнаружения CUDA подготовлены для следующей
сборки приложения; оригинальный RC43 их не содержит. Companion работает
самостоятельно, поэтому переустановка RC43 ради диагностики не требуется.

## 1. Диагностика до установки

Распаковать архив на AGX. Из его каталога:

```sh
sha256sum -c SHA256SUMS
sudo python3 -I robopark-agx.py check
```

Отчёт JSON проверяет идентичность модуля и vendor-маркер DTB, версии ОС/BSP/ядра, RAM, охлаждение, NVMe,
свободное место на корне, число CPU, текущий `nvpmodel`, Docker/Compose/Buildx,
сборочные пакеты, `nvcc` и CUDA Driver API. CUDA проверяется в отдельном процессе
с тайм-аутом. Для Orin ожидается compute capability **8.7**.

`reference_recovery_commit` — источник ожидаемого контракта, не доказательство
того, каким коммитом прошили плату.

Код выхода 2 означает несоответствие либо недостающую готовность; на Mac/Khadas
это ожидаемый безопасный отказ. При другой версии BSP/ядра не обходить отказ:
сначала заново сопоставить установленный vendor-комплект и вычислительные пакеты.

`platform_ready` означает только прохождение базовых проверок companion.
Vendor-маркер DTB проверяется, но это **не подтверждает** всё дерево устройств,
корректность всех UUID, управляемый storage
layout, производительность, запуск модели или готовность восстановленной БД.
Проверка Docker информационная: чистый установщик RC43 умеет готовить Docker.
12 GiB на корне — минимальный запас инструмента, а не расчёт полного места:
отдельно учесть Docker build, БД, вложения, backup и 4–8 GiB для модели.
Для CUDA toolkit может потребоваться больший запас; проверить план APT.

## 2. Native CUDA и сборочные зависимости

Для текущего llama.cpp нужны CUDA toolkit/nvcc, CMake, GCC, git, pkg-config и
SSL/cURL development-библиотеки. cuDNN/TensorRT не являются зависимостями
текущего GGUF runtime. Сценарий подготовки устанавливает только отсутствующие
сборочные зависимости; CUDA добавляется только по явно выбранному пакету.

Сначала проверить настроенные NVIDIA APT-источники на соответствие vendor BSP.
Не подменять их репозиториями JP6, desktop CUDA или инструкцией обновления devkit.
После проверки источников обновить только индекс пакетов:

```sh
sudo apt-get update
sudo python3 -I robopark-agx.py prepare
```

`prepare` выводит план и ничего не устанавливает. Для применения:

```sh
sudo python3 -I robopark-agx.py prepare --apply
```

В обоих режимах сначала проверяется платформа. Затем APT выполняет симуляцию.
Изменение/конфигурация защищённых BSP, драйверов, ядра, загрузчика, systemd/udev,
firmware или vendor-пакетов и любые удаления блокируются. При применении все
пакеты плана закреплены точными версиями; установленные защищённые пакеты
удерживаются на прежних версиях. После установки версии проверяются повторно.
Сценарий не меняет apt sources/holds, не запускает upgrade/dist-upgrade,
не отключает службы и не меняет power mode. Это защита конкретной операции,
не постоянная политика запрета обновлений ОС.

Если `nvcc` отсутствует, получить фактический список toolkit из настроенных
репозиториев и сверить его с установленным JetPack/vendor-комплектом:

```sh
apt-cache search '^cuda-toolkit-[0-9]+-[0-9]+$'
```

Для выбранного имени проверить `apt-cache policy ИМЯ_ПАКЕТА`, происхождение,
точную версию и совместимость с R39.2.0. Затем передать
`--cuda-toolkit 'cuda-toolkit-M-N=ТОЧНАЯ_ВЕРСИЯ'` сначала в `prepare`, после
проверки плана — в `prepare --apply`. Здесь **M-N и ТОЧНАЯ_ВЕРСИЯ — обозначения,
не готовая команда**. Параметр должен называть согласованный пакет toolkit;
сценарий проверяет план, но не сертифицирует совместимость выбранной версии CUDA.
Нельзя выбирать версию до чтения фактических APT-источников платы.
Если APT требует обновить `nvidia-l4t-cuda` или другой защищённый пакет,
остановиться и согласовать целый vendor stack; принудительного обхода нет.

После установки ожидается `/usr/local/cuda/bin/nvcc`. Повторить:

```sh
sudo python3 -I robopark-agx.py check --require-ai
```

Если система использует другой путь CUDA, согласовать штатный CUDA alternatives
с установленным toolkit; произвольные symlink на другую версию не создавать.
Успех CUDA Driver API подтверждает перечисление устройства, но ещё не запуск
llama.cpp с правами `robopark-ai` под ограничениями systemd.

## 3. Хранилище и неизменённый RC43

Предпочтительный вариант для нового хоста — ОС и данные на NVMe. Вариант
«ОС на eMMC, данные на NVMe» также поддержан RC43. Сначала выполнить команды
`storage inspect`, `storage plan`, `storage prepare` и `storage check` из
[руководства NVMe](geacx1-storage.md), используя именно включённый RC43:

```sh
sudo python3 robopark-0.2.0-rc.43.ota verify --json
sudo python3 robopark-0.2.0-rc.43.ota storage inspect
```

Не копировать UUID из примеров. Подготовка отдельного NVMe требует пустую ext4;
диск с резервной копией нельзя выбирать целью. Recovery backup, копия БД
Robopark и подготовка storage layout — разные операции.

SHA-256 опубликованного RC43:

```text
eabeba6cd12fe79b7202bd44fc26b31ad27ca6447f6fb10cea53032359d7714c
```

На подготовленном новом хосте установить RC43 через меню:

```sh
sudo python3 robopark-0.2.0-rc.43.ota
```

Профиль `--preset robopark` предназначен для отдельного преднастроенного старта
и не заменяет восстановление свежей полной копии. Для переноса использовать
штатный путь установки и восстановления своей копии.

## 4. Перенос резервной копии

1. Проверить, что копия приложения сделана с RC43; сохранить её на отдельном
   носителе, сверить контрольную сумму и Alembic head. Копия recovery всей платы
   не заменяет backup приложения с Khadas.
2. Перенести исходный `SECRET_KEY` и требуемые секреты защищённым способом.
   Не выводить их в чат или журналы. Обычный restore не импортирует host secrets.
   Не переносить целиком `host.env`: сохранить профиль и параметры БД нового Orin.
3. Остановить обработчики старого хоста перед включением обработчиков нового:
   один активный Telegram poller, одна очередь исходящих действий, одни расписания.
4. Восстановить штатную копию на **той же версии RC43**. До переключения Tuna
   проверить вход владельца, пользователей/парки, вложения, доступ к интеграциям,
   worker и Telegram. Не включать два источника фоновых записей одновременно.
5. Проверить backup нового хоста, перезагрузку, повторный старт служб и SSH.
   Старый хост и исходную копию сохранить до успешной приёмки.

Подробнее: [перенос данных и секретов](geacx1-storage.md#существующие-khadas-и-перенос-данных)
и [OTA recovery](ota-recovery.md). В копии документа NVMe раздел миграции можно
найти по тексту «Автоматического принятия существующих данных или миграции базы нет».

## 5. Какие возможности Orin используются

| Возможность | Интеграция / критерий приёмки |
|---|---|
| ARM64 CPU | Native Docker build; профиль `orin` при RAM ≥24 GiB и ≥8 видимых CPU |
| NVMe | App/DB/Docker/containerd/логи/backup через управляемый layout; проверка reboot |
| CUDA SM87 | Уже в RC43: pinned llama.cpp, `GGML_CUDA=ON`, `CMAKE_CUDA_ARCHITECTURES=87` |
| Параллельный ИИ | 4 слота, 8192 токена/слот, общий контекст 32768, batching и кэш префикса |
| Общая DRAM | AI `MemoryMax=16G`, swap выключен; API/БД тоже используют ту же RAM |
| Охлаждение | Сохранение vendor fan service; проверка температуры под реальной нагрузкой |
| Мониторинг | Existing host snapshot: CPU/GPU, thermal, memory/I/O PSI; сравнить с tegrastats |
| TensorRT/DLA | В RC43 нет соответствующего backend; движок и выигрыш не подтверждены |
| NVENC/NVDEC/JPEG/VPI | Наличие блоков не ускоряет API/БД; активного consumer в RC43 нет |
| NVIDIA Container Toolkit | Не нужен native llama.cpp и CPU-контейнерам Robopark; отдельный будущий GPU-container use case |

После установки и регистрации полного обученного GGUF по
[инструкции ИИ](local-ai.md) выполнить `sudo /opt/robopark/host-tools/robopark ai-check`.
Без обученной модели генерация остаётся выключенной; базовые веса автоматически
не скачиваются. Проверить `robopark-ai-setup.service`, затем ограниченный
`robopark-ai.service`, GPU offload и отсутствие CPU fallback.

Для измерений использовать [короткие тесты 2/4 API workers](geacx1-performance.md)
и AI 1/5/15 запросов. Одновременно записывать `tegrastats`, PSI и температуры.
MAXN/jetson_clocks не включаются автоматически: режим выбирается по доступному
питанию и охлаждению, а результат подтверждается сравнением p95 и памяти.
Headless-режим можно рассматривать после проверки recovery SSH и потребности
в HDMI/локальной консоли. Это отдельное изменение, в комплект не включено.

## Источники и границы

- [NVIDIA r39.2 Orin](https://docs.nvidia.com/jetson/archives/r39.2/DeveloperGuide/SO/JetsonOrinSeries.html)
- [NVIDIA BSP packages](https://docs.nvidia.com/jetson/archives/r39.2/DeveloperGuide/SD/SoftwarePackagesAndTheUpdateMechanism.html)
- [CUDA for Tegra](https://docs.nvidia.com/cuda/archive/13.2.0/pdf/CUDA-For-Tegra-AppNote.pdf)
- [NVIDIA devkit JetPack setup](https://docs.nvidia.com/jetson/agx-orin-devkit/user-guide/latest/setup_jetpack.html)

Последняя инструкция devkit описывает обновление BSP. На GEACX1 с vendor
carrier её `dist-upgrade` не является шагом этой подготовки. Документация CUDA
подтверждает SM87, но не назначает версию toolkit для ещё не обследованной платы.

Локальные тесты используют синтетическую файловую систему и подменённые ответы
APT/systemd/CUDA. Они не подтверждают физическую загрузку, apt-транзакцию,
ARM64 Docker build, питание, охлаждение, скорость или восстановление данных AGX.
