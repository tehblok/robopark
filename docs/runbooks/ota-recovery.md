# Восстановление OTA

- Прерванная загрузка: снова выберите тот же файл; клиент сверит SHA-256 и
  продолжит с подтверждённого сервером смещения.
- Обновление откатилось: рабочая версия и данные уже восстановлены. Скачайте
  диагностику, устраните указанную причину и только затем повторяйте.
- `rollback_failed`: не удаляйте journal, snapshot, текущий release и marker
  maintenance. Оставьте хост доступным через локальную консоль и соберите
  диагностику.
- Нет доступа к сайту: запустите тот же доверенный `.ota` с USB и выберите
  диагностику или обычное обновление. Чистую установку выбирайте только если
  согласна полная потеря локальных данных.

OTA проверяет пути, размеры, коэффициент сжатия и SHA-256 до извлечения. SHA-256
не аутентифицирует автора пакета.

При нормальном завершении входной файл загрузки удаляется после проверки и
устойчивой записи кэша. Кэш OTA удаляется после terminal receipt; файл активной
прерванной операции сохраняется для resume или rollback. Незавершённые копии и
неиспользуемые входящие файлы с истёкшим TTL удаляет только ограниченное
обслуживание хоста. После успешной сборки частный Buildx builder Robopark
ограничивает кэш размером 2 GB. Образы и снимок, нужные для current и rollback,
сохраняются. При `rollback_failed` автоматическая очистка не должна удалять
артефакты восстановления.

Если старый и действующий теги указывают на один Docker image ID, автоматическая
очистка сохраняет старый тег и запись владения: Docker не даёт удалить тег с
условием «только если он всё ещё указывает на этот ID». Общие слои при этом не
дублируются, но записи и имена тегов могут накапливаться. При диагностике
`image_retention_required` остановите новые OTA и проверьте точный состав
тегов через предпросмотр; не применяйте `docker system prune` или удаление по
общему image ID.

Если сборка оборвалась до записи image ID в квитанцию владения, обслуживание
после устойчивого `failed`/`rolled_back` в OTA-квитанции либо журнале обновления
сверяет метки образа с точной операцией
и релизом, записывает фактический image ID и удаляет только этот ID, если он не
используется и не имеет других тегов. Старые образы без меток, изменённые теги,
образы с общими тегами и `rollback_failed` остаются как `unverified_tags` для
ручной диагностики. Автоматическая очистка не удаляет их по одному имени:
сначала проверьте конкретный тег, image ID и причину удержания на хосте.

На экране владельца «Система» доступны разбивка занятого места и предпросмотр
точных файлов/образов/записей BuildKit. Выполняйте ручную очистку только по
этому предпросмотру. Он не включает том PostgreSQL; команды широкого Docker
prune для этой процедуры не используются. На установленном хосте сначала
снимите фактические размеры, затем решайте, нужна ли очистка.
