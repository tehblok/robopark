# GEACX1: размещение Robopark на NVMe

Эта инструкция относится к готовящемуся `rc.22`: OTA/install-пакету, собранному
из новых исходников ветки `main` с поддержкой storage layout. На момент написания
GitHub Release ещё не опубликован, поэтому используйте только локально собранный
и проверенный кандидат. Опубликованный asset `rc.21` остаётся неизменным и этой
поддержки не содержит: в нём нет описанных ниже команд и защитных проверок. Не
используйте `rc.21` для подготовки хранилища GEACX1.

Формат OTA не изменился: пакет проверяется по SHA-256, но не имеет подписи
издателя. Получайте пакет по доверенному каналу и сверяйте его происхождение.

В примерах задайте путь к фактически собранному кандидату `rc.22`:

```bash
BUNDLE=./robopark-0.2.0-rc.22.ota
sudo python3 "$BUNDLE" verify --json
```

## Два поддерживаемых режима

- `nvme-root` — операционная система и рабочие данные находятся на NVMe. Плата
  уже должна быть загружена с корневой файловой системы на разделе NVMe.
- `emmc-nvme-data` — операционная система остаётся на eMMC, а рабочие каталоги
  Robopark, Docker, containerd и BuildKit размещаются на одном разделе NVMe и
  подключаются через `/srv/robopark-storage`.

Команды Robopark не создают таблицу разделов, не форматируют диск, не переносят
операционную систему и не расширяют корневую файловую систему. Для
`emmc-nvme-data` заранее подготовьте отдельный, полностью пустой раздел `ext4` с
UUID. Не используйте раздел с существующими данными.

## Проверки до подготовки

Сначала зафиксируйте фактическую схему дисков и ёмкость корневой файловой
системы:

```bash
lsblk -o NAME,PATH,TYPE,FSTYPE,UUID,SIZE,RO,MOUNTPOINTS
findmnt -no SOURCE,FSTYPE,OPTIONS /
df -hT /
sudo python3 "$BUNDLE" storage inspect
sudo python3 "$BUNDLE" storage check
```

`storage inspect` — только диагностика. `storage check` проверяет уже управляемую
схему, UUID, точки монтирования и доступность записи; до первой подготовки ответ
`unmanaged` означает прежнюю, неуправляемую схему. Проверку свободного места
выполняйте отдельно через `df`: ёмкость SSD не доказывает, что корневая файловая
система была расширена после прошивки производителя.

Подготовка предназначена для нового хоста без данных Robopark. Если Docker уже
установлен, сначала завершите все контейнеры, включая БД, по их проверенному
списку. Остановка `robopark.service` сама по себе БД не останавливает, а при
Docker live-restore контейнеры могут пережить остановку daemon. Затем остановите
контейнерные службы:

```bash
sudo systemctl stop docker.socket docker.service containerd.service
```

Если на устройстве работают посторонние контейнеры, заранее составьте отдельный
план их остановки и восстановления. `prepare` отклонит работающий Docker,
containerd или контейнеры, занятый раздел, непустую целевую файловую систему,
раздел без UUID и пользовательские корни контейнерных хранилищ.

## Режим `nvme-root`

Убедитесь, что `findmnt /` показывает нужный раздел `/dev/nvme…`, а `df -hT /` —
ожидаемую ёмкость файловой системы. Затем получите план:

```bash
sudo python3 "$BUNDLE" storage plan --mode nvme-root
```

Обычно `--device` здесь не нужен: команда берёт текущий корневой раздел. Если
параметр указан, он обязан точно совпадать с источником `/`:

```bash
sudo python3 "$BUNDLE" storage plan --mode nvme-root --device /dev/nvme0n1p1
```

Проверьте в JSON режим, устройство, UUID, корневую точку монтирования, размер и
поле `confirmation`. Скопируйте подтверждение без изменений:

```bash
sudo python3 "$BUNDLE" storage prepare --mode nvme-root \
  --confirmation 'PREPARE nvme-root <UUID>'
```

Если план строился с `--device`, передайте тот же `--device` и в `prepare`.

## Режим `emmc-nvme-data`

Убедитесь, что `/` находится на eMMC (`/dev/mmcblk…`), а выбранный раздел NVMe —
один пустой раздел `ext4` с UUID. Постройте план, явно указав этот раздел:

```bash
sudo python3 "$BUNDLE" storage plan --mode emmc-nvme-data \
  --device /dev/nvme0n1p1
```

Сверьте устройство и UUID в выводе с `lsblk`, проверьте размер и точную строку
`confirmation`. Только после этого выполните подготовку:

```bash
sudo python3 "$BUNDLE" storage prepare --mode emmc-nvme-data \
  --device /dev/nvme0n1p1 \
  --confirmation 'PREPARE emmc-nvme-data <UUID>'
```

В этом режиме NVMe монтируется в `/srv/robopark-storage`, а постоянные каталоги
подключаются к `/opt/robopark`, `/var/lib/robopark`, `/var/lib/docker`,
`/var/lib/containerd`, `/var/log/robopark` и `/var/backups/robopark`.
Кэш собственного BuildKit builder хранится в Docker volume, который также
находится на NVMe; отдельный `/var/lib/buildkit` не создаётся.

## Интерактивный clean install

Тот же выбор доступен в интерактивном установщике:

```bash
sudo python3 "$BUNDLE"
```

Выберите clean install. При обнаружении NVMe установщик предложит:

- `1` — ОС и рабочие данные на NVMe;
- `2` — ОС на eMMC, рабочие данные на NVMe;
- `3` — оставить текущую неуправляемую схему;
- `0` — отменить установку.

Для второго режима установщик попросит выбрать пустой раздел `ext4`. Он покажет
JSON-план и потребует ввести точную строку подтверждения с UUID. Форматирование и
разметку установщик не выполняет. Если управляемая схема уже находится в
состоянии `ready`, установщик проверит её и использует повторно.

## Проверка после подготовки

До запуска приложения повторите проверки:

```bash
sudo python3 "$BUNDLE" storage inspect
sudo python3 "$BUNDLE" storage check
findmnt -T /
df -hT /
```

Для `nvme-root` отдельная точка `/srv/robopark-storage` не ожидается. Для
`emmc-nvme-data` дополнительно проверьте базовый mount и все bind mount:

```bash
for target in /srv/robopark-storage /opt/robopark /var/lib/robopark \
  /var/lib/docker /var/lib/containerd /var/log/robopark /var/backups/robopark; do
  findmnt -T "$target"
done
df -hT /srv/robopark-storage
```

Они должны вести на выбранный UUID. Только после успешной проверки продолжайте
установку или запускайте службы.

## Существующие Khadas и перенос данных

Устройства Khadas без storage manifest продолжают работать как раньше и
определяются как `unmanaged`. Новая версия сама не переводит их на NVMe и не
меняет текущую схему. Не запускайте `prepare`, если явная миграция не
планировалась.

Автоматического принятия существующих данных или миграции базы нет. Для переноса
нужен отдельный защищённый ручной план:

- сделать проверенный резервный снимок на физически отдельный носитель;
- зафиксировать исходную версию релиза и точный Alembic head базы;
- сохранить исходный `SECRET_KEY` и остальные секреты из `/etc/robopark`;
- восстанавливать приложение на той же версии и точном Alembic head, проверить
  вход, вложения и фоновые задачи, и лишь затем выполнять OTA-обновление.

Если исходный релиз не поддерживает storage guard, сначала подготовьте и
проверьте переход старого хоста на совместимую версию, затем снимайте новую
копию. Старый rc.21 нельзя установить поверх новой управляемой схемы для
восстановления. Обычный restore не импортирует секреты хоста: до запуска
восстановленной БД нужен защищённый перенос прежнего `SECRET_KEY` и пересоздание
потребителей настроек. Не копируйте целиком `host.env`: профиль Orin и параметры
новой БД должны сохраниться. Подробный порядок — в
[архитектуре переноса](../architecture/2026-10-03-geacx1-storage-design.md#перенос-с-текущего-хоста).

## Что ещё нужно принять на физическом устройстве

Эта инструкция описывает реализованные проверки, но физическая приёмка GEACX1
ещё не выполнена. Перед эксплуатацией отдельно проверьте оба режима на реальном
устройстве: перезагрузку, поведение при отсутствующем NVMe, Wi-Fi, recovery SSH,
восстановление из резервной копии и откат. В режиме `emmc-nvme-data` ожидается,
что eMMC загрузится без NVMe, а приложение останется заблокированным до
восстановления правильного диска; это поведение ещё требует аппаратной проверки.
