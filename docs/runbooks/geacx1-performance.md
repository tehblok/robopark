# GEACX1: производительность и короткие измерения

Поддержка двух [схем NVMe](geacx1-storage.md) обеспечивает правильное размещение
данных. Реальная скорость зависит от BSP, режима питания, охлаждения, SSD,
Wi-Fi и нагрузки. rc.23 не включает автоматический MAXN, смену частот,
настройку драйверов или установку CUDA/TensorRT.

## Что ускорено и что измеряется

- При сборке JS/CSS/SVG из `assets` получают готовые gzip-копии. nginx
  использует их только при поддержке gzip клиентом. Исходные файлы остаются;
  HTML, service worker и политика обновлений не меняются. Это уменьшает
  работу сжатия на хосте, но не является измерением ускорения страницы.
- Ручной HTTP-кэш ETag для ревизий и списков Tracker ограничен отдельно
  для каждого семейства: 128 записей, 4 МиБ сериализованных ключей/ETag/тел
  и 12 часов хранения. Это бюджет данных, а не точное измерение JS heap.
  После очистки авторизации поздний 304 не возвращает сохранённое старое тело.
  При перекрывающихся запросах поздний старый 200/304 не заменяет результат
  уже завершившегося более нового запроса. Состояние порядка ответов хранится
  только до завершения последнего запроса, включая его тайм-аут.
- Watchdog публикует необязательные метрики раз в две минуты: частоты CPU,
  доступные частоты/загрузку GPU, температуры CPU/GPU/SoC/NVMe, PSI памяти/I/O
  и данные Wi-Fi. Снимок старше пяти минут помечается устаревшим. Это
  периодический снимок, не непрерывный мониторинг пиков.
- Низкая частота не объявляется троттлингом. PSI показывает долю времени
  ожидания ресурсов, а не задержку SSD или процент заполнения памяти.
- Wi-Fi RSSI показывается только при однозначном источнике; счётчики ошибок
  накопительные, могут сбрасываться при перезапуске интерфейса. SSID, MAC,
  IP, имена сетей и серийные номера не публикуются. NVMe температура не
  заменяет SMART. Неподдерживаемые датчики отображаются как «не измерено».

## Ресурсный профиль

Профиль `orin` выбирается при не менее 24 GiB RAM и восьми доступных CPU:
4 процесса API, потолок API 8 GiB, PostgreSQL 6 GiB,
`shared_buffers=2GB`, `max_connections=100`. Значения — лимиты, не заранее
занятая память. Пулы API остаются ограниченными: до 10 соединений на процесс.

Четыре видимых CPU в энергосберегающем режиме не подтверждают готовность
к четырём процессам профиля Orin. Проверить выбранный режим платы следует
перед установкой/OTA; не обходить проверку правкой `host.env`.
Без доступа к физическому GEACX1 оптимальное число процессов не установлено.

## Изолированная короткая проверка

`scripts/capacity_benchmark.py` создаёт отдельный PostgreSQL-контейнер,
синтетические сессии и локальную заглушку интеграций. Он не принимает URL
production-сайта и не использует его базу/учётные данные. API запускается
отдельными процессами: его cgroup-лимит памяти здесь не применяется, что
явно записано в JSON. Профиль PostgreSQL применяется к временному контейнеру
и проверяется через `SHOW`. Тест проверяет, что запросы обслужили все
заказанные процессы, а не только успешный запуск родителя uvicorn.
Наборы PID при старте, в основной фазе и в стресс-фазе должны совпадать.
Если короткая фаза не охватила все процессы, результат будет отрицательным;
это не доказывает падение процесса. Увеличить число запросов можно через
`--stress-rounds`, не ослабляя проверку покрытия.

Запускать на отдельном приёмочном контуре, до переключения production.
Docker и зависимости dev должны быть установлены. В раздельной схеме
checkout, `TMPDIR` и отчёты должны находиться на уже проверенном NVMe;
каталог для временных файлов заранее создаётся владельцем запуска с mode 0700.
Не указывать чужой каталог или путь к рабочему PostgreSQL volume.

Из корня checkout, заменив `/path/on/nvme/bench` своим каталогом:

```sh
TMPDIR=/path/on/nvme/bench uv run --project apps/api --frozen --extra dev \
  python scripts/capacity_benchmark.py --workers 2 --duration 30 \
  --users 40 --max-in-flight 10 --stress-rounds 1 \
  --output /path/on/nvme/bench/workers-2.json

TMPDIR=/path/on/nvme/bench uv run --project apps/api --frozen --extra dev \
  python scripts/capacity_benchmark.py --workers 4 --duration 30 \
  --users 40 --max-in-flight 10 --stress-rounds 1 \
  --output /path/on/nvme/bench/workers-4.json
```

`--duration` относится к основной фазе: подготовка контейнера, миграции,
холодные/тёплые запросы и очистка занимают дополнительное время.
Сравнивать p50/p95/p99, ошибки, обращения к upstream, RSS и соединения при
одинаковых данных и условиях. Wi-Fi loss/delay в стенде моделируются;
радиоканал, Tuna и реальные ограничения внешних API он не измеряет.
Локальный успешный smoke не подтверждает ёмкость в 200 пользователей.
Восьмичасовой soak не нужен и не запускается автоматически.

## Настройка на плате

1. Зафиксировать vendor BSP, видимые CPU и режим `nvpmodel -q`; сопоставить
   снимки с `tegrastats` при наличии утилиты. Не менять энергорежим во время OTA.
2. Сравнить 2/4 процесса при одинаковой короткой нагрузке, проверить отсутствие
   роста ошибок и давления памяти. Оставить запас ОС, page cache и сборкам.
3. Получить медленные запросы на приёмочной базе и планы `EXPLAIN`; только
   после этого выбирать индексы и `work_mem`. Не увеличивать PostgreSQL
   память или кэш TTL только потому, что в плате 32 ГБ.
4. Отдельно измерить Wi-Fi/Tuna: повторное соединение, реальные RTT/потери,
   объём передачи. Смена power-save допускается после проверки адаптера.
5. GPU/DLA использовать для конкретной функции обработки изображений/OCR,
   если она появится. SQL и HTTP автоматически на GPU не переносятся.

NVIDIA предупреждает, что MAXN не гарантирует лучший результат из-за
ограничения мощности и частот. Требования охлаждения/питания определяет
конкретная плата GEACX1, а не название SoC.
