# Устранение результатов системного аудита

## Цель

Закрыть пункты 2–10 аудита ветки `codex/product-completion`, не меняя намеренно отключённую проверку подписи локального OTA. Результат должен быть пригоден для последующей короткой приёмки и отдельного, явно разрешённого выпуска.

## Ограничения

- Проверку подписи локального OTA не включать и не перерабатывать.
- Не запускать полный API/web suite, soak, нагрузочный benchmark, Docker/VM installation или иной длительный тест без отдельного согласия пользователя.
- В ходе разработки запускать только короткие тесты затронутых модулей, статические проверки и production build, если он укладывается в обычную короткую проверку.
- Не подменять реальную готовность старыми evidence-файлами. Длительные gate-результаты после изменения кода должны оставаться `STALE`/непройденными до отдельного запуска.
- Не расширять собираемые персональные данные. Приблизительная геолокация остаётся по IP, но внешний провайдер должен быть явно настраиваемым и отключаемым.

## Архитектура изменений

### 1. CI и приёмочные доказательства

Обычный Playwright CI не должен обнаруживать длительный soak-сценарий. Soak становится отдельным opt-in project/command с обязательными параметрами. Быстрый browser gate продолжает проверять обычные responsive journeys.

Source-bound acceptance сохраняет fail-closed поведение. После изменений старые отчёты не перезаписываются фиктивным `PASS`: создаётся явный способ пометить их устаревшими либо валидатор продолжает отвергать их до реального повторного прогона. Документация должна объяснять, какие проверки выполнены, какие устарели и какие требуют согласия.

### 2. Серверные уведомления

Обнаружение новых Tracker-задач переносится из пользовательского `GET /tracker/issues` в отдельный lease-owned фоновый poller. Он:

- использует существующий Tracker cache/client;
- ограничивает частоту и объём запросов;
- определяет парк и получателей по существующим правилам доступа и сменам;
- сохраняет курсор/дедупликацию в PostgreSQL, поэтому два API worker не дублируют события;
- не зависит от открытого браузера и не теряет задачу после двенадцатиминутного окна.

Повторная авария после восстановления создаёт новый incident occurrence. Дедупликация действует внутри одного непрерывного инцидента, а не на весь срок хранения старой записи.

Доставка Web Push отделяется от создания внутреннего уведомления. Отправка выполняется ограниченным пулом с общим дедлайном, пакетами и независимым удалением протухших подписок. Ошибка push-провайдера не блокирует request worker и не удаляет внутреннее уведомление.

### 3. Production PWA contract

Добавляется отдельный короткий production-PWA smoke:

- выполняется после `vite build` против содержимого `dist`;
- доказывает регистрацию и активацию настоящего `sw.js`;
- проверяет offline navigation shell;
- подтверждает, что `/api/**`, приватные вложения и пользовательские ответы не попадают в Cache Storage;
- проверяет безопасную активацию обновления при пустой offline-очереди.

Полный reconnect с реальным PostgreSQL относится к отдельному integration gate и не входит в обычный короткий smoke.

### 4. PostgreSQL и фоновые процессы

PostgreSQL gate расширяется короткими HTTP integration tests для критических контрактов:

- повтор одного `client_action_id` не дублирует действие;
- resumable media завершается ровно один раз;
- массовое расписание и push preference работают на migration head;
- конкурентное складское действие сохраняет ожидаемую идемпотентность.

Отдельный короткий lifecycle test запускает приложение с малыми интервалами и проверяет единственного владельца cleanup lease, maintenance barrier и ограниченное завершение фоновых задач. Длительный soak этим не заменяется.

### 5. Ограничение входа

Счётчики login/register переносятся из памяти worker-процесса в PostgreSQL. Операция регистрации неуспеха атомарна, ключ хранится в хэшированном виде, записи имеют TTL и удаляются фоновой очисткой. Перезапуск и переключение между 2–4 Uvicorn worker больше не сбрасывают лимит.

### 6. Приблизительная геолокация

IP-геолокация получает конфигурацию:

- `off` — значение по умолчанию для новых/неявных окружений;
- `ipwhois` — текущий внешний провайдер, включаемый явно;
- возможность в будущем добавить локальную GeoIP-базу без изменения user activity API.

При выключенном провайдере IP и устройство продолжают фиксироваться, `last_location` остаётся недоступным. Вызов внешнего сервиса сохраняет квоту, cache и timeout. В администрировании отображается источник/недоступность без технической ошибки.

### 7. Документация и качество frontend-кода

README и эксплуатационные инструкции приводятся к текущей версии, PostgreSQL и реальному статусу проверок. React lint warnings, затрагивающие корректность render/effect/ref, устраняются в затронутых областях; чисто стилистические массовые переделки не входят в задачу.

## Ошибки и наблюдаемость

- Poller хранит последнюю успешную синхронизацию и краткую безопасную ошибку в health projection.
- Сбой push-доставки виден в ограниченных метриках и логах без endpoint/ключей.
- CI различает `fast browser`, `production PWA`, `PostgreSQL integration`, `load` и `soak`.
- Устаревшие evidence никогда не трактуются как подтверждение текущего дерева исходников.

## Критерии приёмки

1. Обычный CI не запускает soak и не требует `ROBOPARK_SOAK_OUTPUT`.
2. Новая задача порождает внутреннее уведомление без клиентского запроса списка.
3. Инцидент `down → healthy → down` создаёт два уведомления, непрерывный `down` — одно.
4. Web Push имеет ограниченную конкурентность и общий дедлайн.
5. Production service worker проверяется настоящим браузером против `dist`.
6. Критические новые схемы проходят короткие тесты на PostgreSQL migration head.
7. Login throttle общий для worker-процессов и переживает рестарт API.
8. Внешняя IP-геолокация явно включается настройкой; по умолчанию внешней передачи нет.
9. README и release status соответствуют версии и фактическим evidence.
10. Только короткие затронутые тесты выполнены; длительные проверки перечислены как ожидающие разрешения.
