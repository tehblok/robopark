# Знания ремонта и Gemma 4 E4B

## Решение

Владелец выбрал Gemma 4 E4B вместо Bonsai и заменил старую выгрузку тикетов
на `tracker_year_all_parks`. Цель — объяснимые связи между симптомом, кодом
ошибки, компонентом, дефектом, выполненным действием и наблюдаемым результатом.
История задач остаётся доказательной базой, а не набором универсальных инструкций.

Модель работает только на подтверждённом AGX Orin. Текущий Khadas не загружает
веса и не выполняет инференс. Изменение знаний не меняет права инструментов:
закрытие задач и удаление требуют штатного подтверждения, остальные действия
выполняются в пределах роли. Импортируемые тексты не являются инструкциями агенту.

## Знание и его основания

Очищенная выгрузка и агрегаты — подготовленный слой данных. Они сами по себе
не являются базой знаний. Пользователь явно потребовал объяснения и применимые
решения, а не ещё один каталог закрытых задач.

Единица базы знаний — статья, которая отвечает на практический вопрос:
что означает симптом, какие причины нужно различить, что проверить дальше,
как результат проверки меняет следующий шаг и чем подтвердить результат ремонта.
Она указывает применимые узлы и ревизии, альтернативы, отрицательные наблюдения,
неизвестные нормы и соседние темы. Исходный тикет служит основанием отдельного
утверждения, а не переносится в статью целиком.

Первый авторский раздел содержит диагностику камеры, кабеля камеры, питания,
PCU/BRAIN, мотор-колеса, Motor Control, подвески, флажка и корпуса. Отдельные
статьи связывают симптом, HUD, код дефекта, компонент и фактически выполненную
операцию, описывают приёмку и порядок дополнения знаний. Нормативность источника
и достоверность сообщения о ремонте не объявляются проверенными автоматически.

## Слои хранения

1. Оригиналы: неизменяемая приватная выгрузка, чаты, инструкции и справочники.
   В GitHub передаются только в age-архиве с существующим ключом владельца.
2. Свидетельства: нормализованные случаи с источниками, датами, компонентами,
   неизвестными полями и отметками качества. Отдельно хранятся заявленный метод,
   сообщение о выполненном действии и сообщение о результате проверки.
3. Карточки опыта: агрегаты нескольких независимых случаев с одинаковым
   контекстом. Видны альтернативные действия, отрицательные результаты,
   неполные данные и ограничения. Такие карточки имеют trust `unverified`.
4. Авторское знание: объяснения и условные ветки диагностики, составленные
   после чтения инструкций и конкретных свидетельств. Реестр связывает утверждение
   с основанием и отличает сведения документа, наблюдение и редакционный вывод.
5. Поисковый слой: авторские статьи и справочные определения. Неполные PDF,
   агрегаты, переписка и навыки другой ИИ не подмешиваются в эту подборку целиком.
   Инструкция другой ревизии или неизвестного происхождения не становится нормой.

Первоначальная подборка из 119 записей была проверкой подготовки исходных данных,
а не завершённой авторской базой. Она сохраняется как промежуточный результат.

Повторяющиеся слова не устанавливают причину неисправности. `solutionMethod`
означает выбранную категорию действия, а не выполненный ремонт. `closed/fixed`
не доказывает работоспособность. В годовой выгрузке выбраны только закрытые
исправленные задачи: по ней нельзя считать процент успешности метода.
Несколько компонентов одной задачи не создают отдельные доказательства для
каждой детали. `ROBOT_UNSORTED` добавляется перед началом работы, только если
компонента ещё не заполнена; имеющаяся компонента сохраняется. Это временное значение;
его нельзя предлагать как окончательный компонент ремонта.

`0`, `n/a`, пустой код и неизвестное значение различаются с настоящим кодом
дефекта. Неизвестные названия компонентов не преобразуются догадкой.
Связи `relates`/`depends` не означают причинность; дубликаты не увеличивают
число независимых свидетельств. Повтор симптома у робота в течение 30 дней —
кандидат на повторный ремонт, а не доказанный возврат по качеству.

## Подготовка свидетельств

```bash
python3 -m venv output/repair-knowledge-venv
output/repair-knowledge-venv/bin/pip install -r scripts/knowledge-seed-requirements.txt
output/repair-knowledge-venv/bin/python scripts/build_repair_knowledge.py \
  --input 'Данные для базы' \
  --tracker 'Данные для базы/tracker_year_all_parks' \
  --output output/repair-knowledge-current
```

Сборка создаёт новый каталог и не перезаписывает исходники или старый результат.
`tracker/` содержит структурированные случаи, карточки и словарь; `evidence/`
сохраняет очищенные исходные материалы и причины исключения; `seed.jsonl` —
готовый вход существующего сборщика приватного пакета. `report.json` фиксирует
покрытие, ограничения и хеш поискового слоя. Сборка не вызывает внешнюю ИИ.
Это подготовка материалов, не автоматическое авторство базы знаний.

## Сборка авторской базы

После содержательной работы статьи сохраняются в Markdown, а основания —
в `evidence.json` рядом с ними. `scripts/build_authored_knowledge.py` не выводит
правила из частот; он проверяет и упаковывает уже написанное знание:

```bash
python3 scripts/build_authored_knowledge.py \
  --drafts output/repair-knowledge-authored/drafts \
  --output output/repair-knowledge-authored/published
```

Проверяются идентичность заголовков, разрешение связей между статьями, ссылки на
основания, наличие источника и выдержки для нередакционных утверждений, отсутствие
явных приватных маркеров в статьях. Эти проверки не доказывают истинность текста
и не заменяют содержательное ревью. Исходный каталог не изменяется, существующий
результат не перезаписывается.

`articles/` и `README.md` предназначены для чтения человеком. Ссылки S1, S2 и далее
открывают приватные страницы оснований в `evidence/`. `knowledge-map.json`
содержит тематические переходы между статьями, а не граф доказанной причинности.
`seed.jsonl` содержит только статьи, без внутренних идентификаторов, исходных
цитат и закрытого реестра. Статьи импортируются как `note` с `unverified`,
а не выдают редакционную работу за утверждённую сервисную инструкцию.

Каталог с исходными Markdown и evidence сохраняется в зашифрованном пакете.
Ключ остаётся существующим; открытым текстом приватные основания в Git не попадают.
Редакционный цикл «новый случай → изменение утверждения/исключение → проверка»
описан, но его полная автоматизация и экспертная приёмка статей ещё не реализованы.

Для новой подборки использовать `scripts/build_private_knowledge.py
--replace-public`: отсутствующие старые тикеты не добавляются обратно из
публичного seed. Совпадающие source IDs сохраняются. При импорте новой версии
неизменённые исчезнувшие документы переводятся в кандидаты; ручные правки,
отклонения и удаления администратора сохраняются штатными receipts/tombstones.
Без этого флага старое поведение сборщика остаётся совместимым.

Архив свидетельств не монтируется в контекст модели целиком. В запрос попадают
только найденные выдержки с типом источника и ограничениями. Не публиковать
`cases.jsonl`, исходные цитаты, source maps или review pool открытым текстом.

## Обучение модели

Начальный вариант — instruction-tuned Gemma 4 E4B с поиском по базе знаний.
Google публикует [официальный Q4_0 GGUF](https://huggingface.co/google/gemma-4-E4B-it-qat-q4_0-gguf).
E4B имеет 4,5 млрд эффективных и около 8 млрд полных параметров с embeddings;
это не оценка памяти процесса. [Карточка модели](https://ai.google.dev/gemma/docs/core/model_card_4).

Дообучение не заменяет поиск: инструкции, актуальные задачи, новые случаи и
исправления должны обновляться без выпуска новых весов. LoRA целесообразна
для русского ремонтного словаря, краткого формата ответа, выделения полей,
уточняющих вопросов и корректной последовательности вызовов инструментов.
Google описывает [fine-tuning и LoRA](https://ai.google.dev/gemma/docs/tune).

Нельзя использовать сырой закрытый тикет как правильный ответ. Нельзя создавать
эталон из ответа той же модели и считать его проверенным. Для каждого примера
нужны вопрос на момент диагностики, доступные тогда данные, проверенный ответ,
источники и отметка эксперта. Итоговые поля и комментарии после ремонта нельзя
подмешивать во вход, если задача — предсказать решение до ремонта.

Подготовка LoRA проходит отдельным экспериментом:

- Разделить задачи по роботам и связанным/дублирующимся инцидентам; поздний
  период отложить для контрольного теста. Тестовые инциденты не должны попадать
  в тренировочные примеры, подсказки или карточки, используемые при оценке.
- Проверить извлечение компонента/дефекта/действия, отказ при нехватке данных,
  сохранение отрицания, правильные источники и соблюдение прав инструментов.
- Сравнить исходную E4B + поиск с адаптером + тем же поиском на одном тесте.
  Адаптер принимается только при измеримом улучшении без ухудшения безопасности.
- Обучать на отдельной машине с подходящим GPU после отдельного выбора среды;
  отправка внутренних данных внешнему провайдеру не входит в локальную сборку.

Текущий механизм после операторской приёмки добавляет активный документ опыта
в пределах парка с trust `experience`; это сообщение о конкретном ремонте,
а не автоматическая правка авторской статьи. Он не обновляет веса. Синтез нового
общего правила требует отдельного разбора оснований и проверки применимости.

## Что проверяется на AGX

Работоспособность конкретного GGUF, CUDA-сборки, шаблона чата, токенизации и
JSON/tool-call контрактов проверяется на самой плате. Наличие поддержки модели
в upstream не доказывает скорость на GEACX1.

Для 5–15 одновременных пользователей измеряются очередь, TTFT, скорость ответа,
p95 полной задержки, общая память, температура и отмена запросов при нагрузке
1/5/10/15. Сначала текст и ограниченный контекст. Обещать 15 параллельных генераций
по размеру файла нельзя: нужны управление очередью и проверка batching.
Существующая последовательная очередь пока не считается проверенной на этот пик.
Восьмичасовой тест не проводится по указанию владельца.
