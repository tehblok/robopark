# Уточнение RC14 — 2026-10-16

Живая проверка установленной RC13 выявила ещё один результат провайдера:
после Passport/MFA основная страница `oauth.yandex-team.ru/authorize` отвечает
200, остаётся открытой и показывает копируемый токен. RC13 исключала этот
путь в JS, нативном обработчике и политике credentials. RC14 согласует все
три проверки; для `/authorize` ожидаются правильные уникальные state,
client_id и response_type. Неизвестные вспомогательные параметры провайдера
не заменяют эти проверки. Проверка личности владельца остаётся обязательной.

Регрессия воспроизводится синтетической страницей в настоящем WKWebView с
тем же изолированным content world и штатной политикой credentials.
Подтверждение теста не заменяет фактический корпоративный вход после установки.

## История RC13

Подтверждено на установленной RC12: корпоративный провайдер завершает вход
на `oauth.yandex-team.ru/` и показывает модальное окно с токеном. Перехода на
ожидавшийся `verification_code` не было; приложение не сохранило OAuth/cookie.

RC13 поддерживает оба результата: fragment callback с проверкой state и
страницу выдачи токена. Обработчик страницы работает только в основном фрейме
собственного окна входа, в изолированном мире WebKit, на точном HTTPS origin и
двух путях завершения. Результат связан с конкретной попыткой входа; старые
окна, подфреймы и результаты после смены аккаунта не принимаются. Считывается
полное значение видимого поля, без буфера обмена, пароля или снимка экрана.
Любой кандидат сначала проходит `/v3/myself` и сравнение владельца Mac.
Отсутствующий срок действия хранится как неизвестный, с повторной проверкой
личности; не заменяется вымышленным временем истечения.

Tracker/Inventory получают OAuth только на предусмотренных API hosts.
Emergency получает отдельную cookie той же Passport-сессии. Inventory ACL
проверяется отдельно на разрешённом сервером роботе; единый вход не выдаёт
дополнительных прав. С RC12 секреты хранятся в каталоге текущего пользователя
Robopark (0700/0600), а Keychain используется только для старого переноса.

Сравнение с исходниками предоставленного установщика Stefania 0.4.3.33:
автоматический путь использует authorization code + PKCE + loopback callback;
ручной путь выдаёт копируемый токен. MULTI_TOKEN_1 раздаёт один токен дочерним
потребителям согласно зарегистрированным правам. У Robopark другой client ID;
чужие настройки и callback-порты не переносились. Переход на PKCE требует
подтверждённой регистрации callback собственного OAuth-приложения.

Ниже — исходная исследовательская запись; старые упоминания Keychain описывают
предыдущие версии, а не хранение RC12/RC13.

# Единый первоначальный вход на Mac: исследование и контракт

Проверено 15.10.2026. Статус: требования подтверждены владельцем; мастер корпоративного подключения реализован в рабочей тестовой ветке, личный вход в живые сервисы ещё не проверен. Это не описание опубликованного rc.2.

## Требование

Один мастер первоначального входа после установки, затем сохранённая сессия владельца. Mac не принимает другую учётную запись Robopark. Корпоративные запросы выполняются от владельца: оператор — для себя и механиков его парка в пределах прав; admin/royal — только для себя. Балансировка ресурсов не переносит корпоративную личность на другого владельца.

«Один вход» означает единый сценарий подключения и проверку одной личности. Он не означает один универсальный токен для всех служб или обещание вечной сессии. Повторный вход требуется при отзыве, истечении, MFA/политике корпоративного провайдера. Пароль не сохраняется.

## Подтверждённые источники

- [Tracker: доступ к API](https://docs.yandex-team.ru/tracker/api/access#about_OAuth). Актуальная документация описывает личный OAuth 2.0, разрешения `startrek:read` и `startrek:write`. Общедоступное приложение для получения временного токена предназначено для тестирования; для production требуется своё OAuth-приложение под staff-роботом. Владение OAuth-приложением и пользователь, от имени которого выполняется запрос, — разные сущности: пользовательские запросы остаются личными.
- [Tracker: информация о текущем пользователе](https://docs.yandex-team.ru/tracker/api/users/get-user-info). `GET /v3/myself` возвращает `login`, `uid`, `trackerUid`, `passportUid`. Тип ID следует хранить явно; нельзя сравнивать разные пространства идентификаторов. Локально установленный SDK ещё использует `/v2/myself`.
- [Историческая копия инструкции API](https://wiki.yandex-team.ru/zen/support/wfm/suptech/orabotesapi), редакция 2022 года: описаны OAuth и cookie `Session_id`. Это историческое подтверждение, не гарантия актуального cookie-контракта. Каноническая Wiki `tracker/api` вернула 403; отказ не обходился.
- Локальная проверенная ранее матрица `fleetops-knowledge/references/auth.md` и `inventory-sdc/references/inventory-api.md`: личный корпоративный OAuth использовался для Tracker и Inventory; Emergency имеет отдельные ACL и текущая Mac-реализация использует cookie после Passport. Это исторические наблюдения сентября 2026, а не свежая проверка всех API.
- [Личная страница о парках](https://wiki.yandex-team.ru/users/tehblokdan/avtomatizacija-raboty-parkov) помечает прежнюю ручку Inventory устаревшей и ссылается на `tools-inventory.sdc.yandex-team.ru/api/v1/docs`. При чтении документации получен 401 как без авторизации, так и с доступным Inventory OAuth. Последующая проверка `/v3/myself` показала, что сохранённый профиль принадлежит **роботу**, а не личному аккаунту; первоначальная характеристика «личный» была ошибочной. Это ограничение доступного способа входа, а не доказательство удаления старого API. Содержимое страницы и секреты не копируются в репозиторий.
- Живая проверка сохранённого профиля: Tracker `/v3/myself` — 200, действующий робот; Emergency `/` с тем же OAuth — 403. Проверка без credentials направляет Emergency в корпоративный Passport. Эти результаты не подтверждают работу личного OAuth в Emergency.
- [Публичная документация OAuth](https://yandex.com/dev/id/doc/ru/tokens/debug-token) подтверждает формат callback fragment `access_token`/`expires_in`; [code flow](https://yandex.ru/dev/id/doc/ru/codes/code-url) описывает PKCE. Это публичный Яндекс ID, а не доказательство включения PKCE/refresh на корпоративном OAuth-клиенте. В тестовой сборке применяется документированный корпоративный временный клиент; production требует собственного приложения.

## Что пока не подтверждено

Поддержка PKCE/refresh token/нативного callback конкретным корпоративным OAuth-приложением; общий cookie-контракт для всех трёх служб; штатный способ входа и проверки личности нового tools-inventory. Поиск docs через IntraSearch не дал доступного слоя; прямое чтение доступного Docs Tracker сработало. Отсутствие результатов поиска не означает отсутствие документации.

## Реализация по подтверждённым контрактам

1. Устройство получает неизменяемого владельца из аутентифицированного server-side enrollment. Выход не освобождает привязку. Старые установки восстанавливают owner ID только по подтверждённому устройством каналу.
2. Robopark открывает штатный корпоративный вход; сессии каждого сервиса хранятся раздельно в Keychain, с привязкой к instance/device/owner/подтверждённой корпоративной личности. Cookie передаются только соответствующему разрешённому хосту; redirects с credentials не выполняются.
3. Успешный вход ещё не означает готовность gateway. Отдельно проверяются текущая личность, её соответствие серверной привязке и доступ к каждой операции. Недоступный сервис отображается отдельно, другие разрешённые функции продолжают работать.
4. Поддержание сессии использует только подтверждённый провайдером механизм. При 401 — `reauth_required`; при 403 — `access_denied`; при сетевом сбое — `network_unavailable`. Эти состояния не заменяют друг друга и не переключают запрос на чужую учётную запись.
5. Вход в Robopark и вход в корпоративный IdP нельзя объединять доверием к заявленному клиентом логину. Для настоящего единого SSO серверу нужен проверяемый ответ IdP или уже установленная доверенная привязка. Произвольное создание/выдача роли по строке логина исключены.

Новые корпоративные разрешения, OAuth-приложение и внешние записи в рамках исследования не создавались. Production не менялся.

## Реализованный мастер в тестовой ветке

После первого входа в Robopark и привязки устройства открывается один ephemeral WKWebView: OAuth → Emergency через общий корпоративный Passport. OAuth callback принимается только для точного host/path и одноразового криптографического `state`. Личность OAuth проверяется живым `/v3/myself` и сравнивается с `owner_tracker_login`, полученным из аутентифицированного ответа сервера.

Для Emergency разрешён только один secure `Session_id` корневого домена `.yandex-team.ru`, path `/`, применимый и к Emergency, и к Tracker. Этот конкретный Cookie header **отдельно** проходит `/v3/myself`; совпадение OAuth-пользователя само по себе не подтверждает владельца другой cookie. Host-only, неоднозначные и старые непроверенные cookie не включают шлюз. Если исторический cookie-контракт больше не поддерживается, интерфейс показывает невозможность проверки, не использует чужую или серверную сессию.

Пароль не сохраняется. OAuth и проверенная cookie хранятся в Keychain владельца. Проверка повторяется при подключении и периодически; logout закрывает окно и отменяет ожидающий результат. Смена серверной привязки корпоративного логина инвалидирует сохранённые корпоративные credentials. Состояния входа, отказа в доступе и отсутствия сети различаются.

Это **один мастер корпоративного подключения после входа в Robopark**, а не уже готовая замена первичного входа Robopark на SSO. Для последней серверу нужен собственный проверяемый OAuth/OIDC контракт. Автоматическое продление корпоративного токена без подтверждённого refresh flow не заявляется.

Локальные Swift проверки владельца, callback, cookie и жизненного цикла пройдены; физический вход сотрудника через MFA в целевой сети остаётся обязательной приёмкой тестового выпуска.
