# Подтверждение происхождения OTA — предложение

Статус: 1 октября владелец выбрал «Сохранить нынешний формат OTA».
Предложенный переход не реализуется; действующий v1 и обновление rc.16 сохраняются.

Текущий `hash-only-ota-v1` проверяет структуру, размеры и SHA-256 файлов.
Пароль/TOTP подтверждают полномочия устанавливающего владельца. Если пакет
подменён до выбора файла, его собственные корректные хэши не подтверждают
издателя. Это остаточный риск ручной установки кода с системными правами.
Отсутствие подписи сейчас намеренно закреплено
`tests/host/test_repository_governance.py`.

Предлагаемый переход сохраняет обновление установленного rc.16:

1. Выпустить совместимый v1-пакет перехода с новым проверяющим модулем и
   закреплённым открытым ключом. Сам переход доставляется через уже доверенный
   текущий процесс; он не получает задним числом защиту цифровой подписью.
2. Следующие пакеты v2 подписывать отдельным ключом выпуска. Подпись покрывает
   точные байты манифеста, содержащего версии, ограничения и хэши всего payload.
   API и host проверяют подпись независимо до сборки или исполнения кода.
3. После перехода отклонять новые неподписанные пакеты. Откат уже проверенной
   установленной версии остаётся доступным; проверки старых архивов для
   совместимости явно отделяются от допуска нового обновления.
4. Закрытый ключ хранить вне репозитория, OTA и web-сборки, с правами `0600`.
   Владельцу нужна отдельная резервная копия. Потеря ключа потребует локальной
   процедуры восстановления доверия; сетевой обход проверки не добавляется.
5. Смену доверенного ключа выполнять через обновление, подписанное прежним
   ключом, либо через явно подтверждённое локальное восстановление. Проверить
   подмену содержимого/манифеста, неизвестный ключ, downgrade и переход rc.16.

Альтернатива — сохранить v1 и ручное доверие к источнику каждого пакета.
В этом случае защита от подменённого издателя не заявляется, даже при наличии
TOTP, HTTPS и совпадении всех контрольных сумм.
