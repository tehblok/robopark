# Быстрое и корректное оформление ремонта

Владелец одобрил реализацию 4 октября 2026: минимум времени пользователя, простая форма, максимум обоснованной автоматизации. Это обычный workflow Robopark на всех хостах. Локальный ИИ остаётся отдельной будущей функцией только AGX Orin.

## Результат этого изменения

- Удалить произвольную подстановку ROBOT_SUSPENSION при взятии задачи.
- Взятие задачи — одна кнопка без предварительного выбора детали. По уточнению владельца перед переходом в работу пустое поле получает временную `ROBOT_UNSORTED`; существующие реальные компоненты сохраняются. Числовой ID временного значения определяется по активному каталогу очереди, а не закрепляется в коде.
- При завершении временная компонента заменяется реальной. Детали имеют понятные названия и поисковые синонимы; автоматически предлагается только однозначное совпадение полного названия с заголовком. Широкие поисковые синонимы не участвуют в автоматическом выборе.
- Связь детали, дефекта и действия определяет порядок подсказок. Все канонические значения остаются доступны; статистика прежних ремонтов не задаёт запретов и не подтверждает выполненное действие.
- Завершение: понятное название неисправности, выполненное действие, фото и необязательное уточнение. Уже заполненные допустимые значения используются как начальные. Пользователь может изменить выбор.
- Полный структурированный отчёт формируется из подтверждённых пользователем полей. Его не нужно заново печатать. Legacy-клиенты без структурированных полей сохраняют прежнее требование комментария.
- Компоненты, дефект и способ устранения записываются до передачи оператору через существующий outbox. При конкурирующей правке полей — явное needs_attention, без молчаливой перезаписи. Повтор доставки распознаёт уже применённый результат.
- Online и offline команды передают одинаковые поля. Ошибка отправки сохраняет заполненную форму; повтор использует прежнюю идемпотентность.

## Контракт

`GET /tracker/issues/{key}/repair-options` (обычные scope/RBAC):

```
{
  issue_key: string,
  components: [{id: string, label: string, tracker_name: string | null,
    aliases: string[], defect_codes: string[], solution_methods: string[],
    defect_method_suggestions: {[defect_code: string]: string[]}}],
  selected_component_ids: string[],
  suggested_component_ids: string[],
  suggestion_reason: string | null,
  defect_code: string | null,
  solution_method: string | null,
  solution_methods: [{code: string, label: string}],
  defect_method_suggestions: {[defect_code: string]: string[]},
  field_snapshot: {component_ids: string[], defect_code: string | null, solution_method: string | null}
}
```

`field_snapshot.defect_code` сохраняет исходное значение поля, тогда как `defect_code` — только распознанный допустимый код для начального выбора. Компоненты идентифицируются ID, не отображаемым названием. Каталог ограничен очередью, исключает архивные значения для нового выбора; существующие значения нельзя терять из-за неполного каталога.

Claim сохраняет совместимость с необязательным JSON `{component_ids: string[]}`, но новый процесс не использует этот параметр для итоговой классификации. При пустом поле очередь сначала выполняет разрешение и запись временной компоненты, затем переход в работу. Если активной `ROBOT_UNSORTED` нет или имя неоднозначно, переход не выполняется, а синхронизация требует проверки справочника. Уже заполненные компоненты не перезаписываются.

Submit-review сохраняет multipart defect_code/photo/comment и принимает необязательное поле `repair_fields` — JSON `{component_ids: string[], solution_method: string, expected: <field_snapshot>}`. Offline payload использует тот же объект. Новый пакет полей выполняется единым действием `set_repair_fields` с защитой от устаревших значений и проверкой разрешённых кодов/компонент.

`ROBOT_UNSORTED` не входит в выбор итоговой детали и не может оставаться в structured target, включая архивное временное значение. В исходном snapshot оно сохраняется для проверки конкурирующих изменений. Legacy submit при временной компоненте требует заполнить новую форму (`repair_fields_required`); уже существующие отчёты и задачи с реальной компонентой сохраняют прежнюю совместимость.

Методы: CHANGE (Заменил), REPAIR (Отремонтировал), MAINTENANCE (Обслужил), DIAG (Провёл диагностику), CONFIG (Настроил), HARD RESET (Сбросил настройки), INSTALL (Установил), RESTART (Перезапустил). Это выбор выполненного действия; из текста заявки нельзя делать вывод, что действие уже выполнено.

## Устойчивость

Не менять права, требования фото, проверку оператором, порядок надёжной очереди, формат OTA v1 или существующие миграции. Сохранить обработку уже поставленных legacy-действий: queued `catalog` и прежние markerless starts не переинтерпретируются новым правилом. Новые методы SDK используют штатный version-aware update, ограниченные чтения и существующую обработку ошибок.

Нельзя загружать частные экспорты/историю в исходники, OTA или Git. Изменение не включает автоматическое закрытие связанных задач, движок произвольных правил, импорт базы знаний или ИИ-инференс.

## Проверка

Временная компонента до перехода статуса и замена реальной до проверки; пустой/неоднозначный/архивный каталог; права/очередь; повтор доставки после timeout; изменение человеком между чтением и записью; новая и legacy offline-команда; понятные названия и полный ручной выбор; автоматический структурированный отчёт; восстановление формы после ошибки; мобильная доступность. Без восьмичасового теста.

## Реализованное поведение и совместимость

- Частые действия видны сразу; остальные доступны через «Другое действие». Форму проверено на телефоне и компьютере.
- После подтверждения взятия назначенной задачи поля заранее попадают в существующий изолированный по пользователю и правам IndexedDB-кэш. До подтверждения snapshot не загружается, чтобы не сохранить поле до записи временного значения. При временном отказе справочника данные доступны после перезагрузки. Если задача ещё не была открыта и данных нет, интерфейс предлагает повторить загрузку.
- Уточнение входит в один структурированный отчёт и онлайн, и через офлайн-очередь. Новая форма не создаёт отдельную обязательную отправку комментария.
- Исходный snapshot сравнивает именно поля ремонта, без чувствительности к порядку компонент. Запись использует версию того же свежего Tracker resource; HTTP 409/412/428 обрабатываются как конфликт. Поля, отчёт и фото повторно не отправляются, если уже подтверждено их применение.
- При конфликте до приёма отчёта можно явно загрузить актуальные поля, сохранив фото и уточнение. При конфликте доставки или удалении компоненты проверка возвращается механику для исправления.
- Исправленный отчёт замещает недоставленную цепочку прежнего отчёта. Она сохраняется в истории, но больше не повторяется и не возвращает новую проверку в ошибку, в том числе после передачи задачи другому механику.
- Прежние очереди действий продолжают обрабатываться. Миграции и формат OTA v1 не менялись. В этой поставке нет загрузки моделей, импорта частных выгрузок или ИИ; она работает и на Khadas.


## Подсказки из текста и примеров ремонта

Форма показывает до трёх предложений по уже загруженным названию/описанию,
пользовательским комментариям текущего ремонта и текущему уточнению. Подстановка
происходит только по нажатию. При замене показано «прежнее → предлагаемое»;
отмена возвращает прежние поля, не трогая фото и текст. Ручная правка полей
сбрасывает отмену, чтобы она не уничтожила последующие изменения пользователя.
Подсказки можно скрыть до закрытия формы.

Чистая функция в браузере сопоставляет слова и формы слов с текущим каталогом.
Перекрывающееся упоминание «кабель камеры» приоритетнее слова «камера» внутри него;
отдельные упоминания разных деталей в одном предложении считаются неоднозначными.
Позиционные детали требуют совпадения позиции. Коды дефектов не исправляются
приблизительно. Неопределённость оставляет человеку полный ручной выбор.
Действие может предлагаться только по утвердительной записи о выполненной работе
в текущем уточнении; планы, вопросы, отрицания, цитаты и сообщения истории его
не подтверждают. Это ограниченные эвристики, а не понимание произвольного текста.

Добавочный `repair_context_eligible` в timeline по умолчанию false. Сервер отмечает
только локальные user-комментарии, связанные с действием comment текущего активного
claim после успешного start и последнего закрытия. Старые недоставленные,
замещённые отчёты, служебные сообщения, подпись «Фото» и сырые Tracker-комментарии
не используются. Передача смены сохраняет текущий цикл по истории действий.
У старого сервера без поля предложения остаются доступны по названию/описанию
и текущему уточнению. Дополнительных внешних запросов для подсказок нет.

Частная выгрузка из 4175 тикетов проверена отдельно: для анализа ключевых слов
использованы только заголовок и описание без комментариев и истории, чтобы
итог ремонта не попадал в исходные признаки. Победитель сочетания выбирался
по обучающей части, а затем проверялся на отложенной части со стабильным
разделением по хэшу имени файла. Общие симптомы вроде «не открывается» и
«не включается» не дают надёжного указания на конкретную деталь.
Три проверенных сочетания детали и дефекта поднимают CHANGE в списке действий:
MotorControl + EL-02, переднее левое мотор-колесо + CH-03, флаг + BD-02.
Это навигация по историческим примерам; она не подставляет выполненное действие.
Другие дефекты и способы ремонта доступны независимо от истории.

В код и OTA входят только обобщённые правила. Частные экспорты, тексты, авторы,
идентификаторы тикетов и промежуточные отчёты остаются в игнорируемых каталогах.
Автоматического обучения, закрытия тикетов и обращений к модели в этой функции нет.
