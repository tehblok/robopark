# GEACX1: два варианта хранения Robopark

Дата: 2026-10-03. Статус: реализовано в кандидате rc.22; автоматические проверки описаны в [отчёте](../reviews/2026-10-03-geacx1-storage.md). Физическая приёмка на GEACX1 ещё не выполнена. Исторические формулировки ниже описывают исходный код rc.21 и принятые требования.

## Цель и исходные условия

Поддержать GEACX1 / AGX Orin 32 ГБ / 510JX0 r3.0 с JetPack 7.2 и NVMe 1 ТБ в двух равноправных вариантах:

1. ОС и рабочие данные на NVMe.
2. ОС на eMMC, рабочие данные и сборки Robopark на NVMe.

Пользователь подтвердил модель GEACX1 и JetPack 7.2; ревизия 510JX0 r3.0 и модуль P3701-0004 указаны в его recovery-репозитории и требуют сверки с самой платой. Подключение — Wi-Fi. Постоянного физического доступа к терминалу нет. Сохраняются текущие OTA v1 без подписи издателя, проверка SHA-256, штатная авторизация, отдельный TOTP для root-терминала и возможность отката. Восьмичасовой тест не проводится.

Основа исследования: Robopark `7c1635c178991a6b2cb5cb4c436a1eecd89132a1` и [geacx1-recovery-validation, commit 71568b9](https://github.com/tehblok/geacx1-recovery-validation/tree/71568b9d54c073cecece7dfd622b5b4e06145129). Исследованы README и исходники recovery; многогигабайтный vendor payload и физическая плата в этой работе не проверялись.

## Что уже есть, что требуется добавить

Robopark выбирает профиль `orin` при RAM от 24 GiB и не менее восьми обнаруженных CPU: четыре процесса API, лимит API 8 GiB, PostgreSQL 6 GiB, `shared_buffers=2GB`, 100 соединений. Это ресурсный профиль, а не доказательство работы CUDA. В `capabilities.py` ускоритель обнаруживается информационно; потребителя аппаратной обработки изображений пока нет.

Production renderer использует штатные `/opt/robopark`, `/var/lib/robopark` и Docker volume PostgreSQL. Обнаружение NVMe не меняет эти пути. Настройки альтернативного data source в ручном Compose не являются поддержкой диска в OTA-установщике.

Текущий clean-install отклоняет даже пустые, но уже существующие `/opt/robopark` и `/var/lib/robopark`. Поэтому инструкция «создать bind mounts и запустить старый установщик» недостаточна. Нужен согласованный сценарий подготовки, проверки пустоты и установки. Отдельно требуется адаптация удаления: mountpoint нельзя обрабатывать как обычное дерево для безусловного рекурсивного удаления.

## Сравнение вариантов

| Вопрос | ОС на NVMe (`nvme-root`) | ОС на eMMC, данные на NVMe (`emmc-nvme-data`) |
|---|---|---|
| Прошивка GEACX1 | Режим `nvme`: внешний rootfs и QSPI | Режим `emmc`, затем подготовка NVMe как диска данных |
| ОС и драйверы | NVMe; загрузочная прошивка остаётся отдельной частью платформы | eMMC |
| База, файлы, контейнеры, сборки, OTA | NVMe | NVMe |
| Сложность | Меньше отдельных монтирований | Нужны монтирования, контроль их порядка и наличия диска |
| Отказ NVMe | Штатная ОС с этого диска не загрузится; потребуется Recovery или заранее испытанный запасной boot | ОС на eMMC может загрузиться, приложение блокируется; возможна независимая диагностика |
| Переустановка ОС | Прошивка NVMe может уничтожить данные на нём | eMMC-проход позволяет отделить ОС от диска данных; сохранность проверяется перед операцией, доступ к старой БД восстанавливается отдельно |
| Ёмкость eMMC | Не ограничивает rootfs | Нужен запас для ОС, совместимых драйверов и их обновлений; большие SDK, кэши и модели не устанавливаются бесконтрольно |

Оба варианта используют NVMe для нагрузки приложения. Выбор определяется удобством восстановления, а не обещанием одинаковой производительности без измерений. При редком физическом доступе предпочтителен `emmc-nvme-data`, если независимый аварийный доступ действительно проверен. `nvme-root` проще обслуживать при наличии готового USB Recovery и внешней копии данных.

### Границы recovery-репозитория

В `recovery_core.py` eMMC использует `flash.sh geacx1-32gb-jp72 mmcblk0p1`, NVMe — `l4t_initrd_flash.sh` с `--external-device nvme0n1p1` и vendor XML. Это описание существующего кода, не команда для выполнения на текущем сервере.

**Пункт `both` записывает две ОС последовательно, а не создаёт схему eMMC + диск данных.** Он требует повторного Force Recovery и второй записи QSPI. Не использовать его для подготовки NVMe с рабочими файлами.

NVMe-команда не задаёт размер APP самостоятельно. Vendor `flash_l4t_external.xml` находится в payload, поэтому по изученным файлам нельзя утверждать, что rootfs займёт весь 1 ТБ. После прошивки обязательны проверка GPT, размера APP и доступного места через `lsblk`, `findmnt`, `df`. Расширение раздела разрешено только отдельным проверенным сценарием; нельзя автоматически изменять GPT работающего сервера. Базовый вариант использует штатную разметку BSP. Отдельный раздел данных на том же SSD не вводится без проверки совместимости с прошивкой и восстановлением.

В репозитории используется NVIDIA Sample Root Filesystem R39.2.0 вместе с BSP/ядром/сервисами производителя. Это не подтверждённая копия заводского rootfs. CUDA, cuDNN и TensorRT не включены в базовый recovery-образ. Нельзя подменять этот BSP образом обычного Developer Kit или устанавливать сохранённые в репозитории пакеты JP6/JP4 поверх JP7.2.

## Одинаковые пути приложения в обоих режимах

Приложение и OTA сохраняют штатные пути. Для `nvme-root` они обычные каталоги корневой файловой системы NVMe. Для `emmc-nvme-data` предлагается один ext4-раздел, подключённый по UUID в `/srv/robopark-storage`, и следующие bind mounts:

| Источник под `/srv/robopark-storage` | Путь, видимый существующему коду | Назначение |
|---|---|---|
| `application` | `/opt/robopark` | Релизы, staging релизов, current/previous, host-tools |
| `state` | `/var/lib/robopark` | Вложения, данные бота, задания, загрузки OTA, package cache, rollback/restore state |
| `docker` | `/var/lib/docker` | Docker metadata, volumes, в том числе PostgreSQL, и данные используемого storage driver |
| `containerd` | `/var/lib/containerd` | Image content и snapshots при соответствующем backend |
| `logs` | `/var/log/robopark` | Журналы приложения и host operations |
| `backups` | `/var/backups/robopark` | Локальные резервные копии |

Это базовая карта для стандартного Docker. До применения нужно прочитать фактические DockerRootDir и containerd root: нестандартные пути нельзя молча оставить на eMMC или перезаписать. Общий Docker с посторонними приложениями требует отдельного плана обслуживания. Каталоги Docker и containerd остаются раздельными.

Bind mounts сохраняют контракт абсолютных путей и проверки, запрещающие symlink-каталоги. Staging релиза и его конечный каталог должны находиться на одной файловой системе для атомарного rename. Нельзя разделить `/opt/robopark/releases/.staging-*` и релизы между eMMC и NVMe.

На eMMC в раздельном режиме остаются `/etc/robopark`, конфигурация ОС/сети, ограниченный journald и небольшой модуль проверки хранения. Его код и журнал не зависят от `/opt/robopark`, Docker или PostgreSQL. `/run` остаётся временной файловой системой ОС. Большие временные файлы сборок и восстановления направляются на NVMe; всё `/tmp`, `/var` или `/home` целиком не переносится. Кэш APT очищается/ограничивается отдельно, домашние каталоги и системные данные не становятся неявной частью миграции приложения.

В режиме `nvme-root` не создаётся второй набор bind mounts на тот же диск. В обоих режимах проверяется фактическое расположение каждого пути, включая Docker volume БД, а не только наличие устройства с именем `nvme0n1`.

Существующие хосты, включая Khadas, без storage manifest продолжают использовать свой прежний layout. OTA не должна автоматически переносить их данные или требовать NVMe только из-за появления поддержки GEACX1. Новая схема включается явным сценарием подготовки/миграции.

## Установка и защита от отсутствующего диска

Названия режимов выше — предлагаемый интерфейс, пока не существующие параметры CLI.

1. Установщик читает модель, BSP, корневую ФС, накопители, UUID, размеры, содержимое целевых каталогов и используемые Docker roots. Только предлагает обнаруженный режим; не выбирает произвольный «самый большой диск».
2. Показывает выбранный накопитель и план размещения. Существующие разделы и файлы не форматирует автоматически. Создание файловой системы — отдельная явно подтверждённая операция над конкретным устройством.
3. В раздельном режиме готовит хранение и системные зависимости до первого запуска Docker/установки пакетов, которые могут запустить daemon. Сохраняет небольшое root-owned описание схемы вне удаляемых application roots, например `/etc/robopark-storage/layout.json`: версия схемы, режим, UUID/PARTUUID, идентификатор диска при наличии, ожидаемые bind sources и targets. Секретов в нём нет.
4. Clean-install разрешает существующие каталоги только как принадлежащие этой подготовке, проверенные и пустые mount targets. Общая защита от установки поверх чужих данных сохраняется. Повтор после прерывания различает завершённый шаг и неподтверждённое состояние.
5. До запуска writer-сервисов проверяет настоящий mount, источник и подкаталог bind mount, UUID, запись, свободное место и inode. Одного `Path.exists()`, файла-маркера или `RequiresMountsFor` недостаточно.

Зависимости нужны не только `robopark.service`, но и Docker/containerd, включая socket activation, updater, команды, backup, bot, timers/path units и прямые CLI-входы в операции записи. Проверка хранения должна запускаться до исполнения кода с NVMe. Конкретные mount units и связи systemd выбираются по реальным пакетным units, включая NVIDIA runtime; конфигурация NVIDIA не заменяется пустым `daemon.json`.

Отсутствующий NVMe не должен быть обязательной зависимостью `local-fs.target`/загрузки аварийной сети. Для базового mount и bind mounts используется семантика необязательного для ОС подключения (`nofail` либо эквивалентные native units), ограниченное ожидание устройства и отсутствие цепочки, переводящей весь boot в emergency. Для writers, напротив, эти mounts обязательны. `nofail` не даёт разрешения писать в пустой каталог: независимо проверяются mount identity и guard. Холодная загрузка без NVMe с достижимым аварийным доступом — обязательная приёмка, а не вывод из содержимого `fstab`.

Перенос существующего Docker root выполняется только в обслуживании после подтверждённой остановки контейнеров, PostgreSQL и использующих диск процессов. Текущий `systemctl stop robopark` останавливает worker/web/api, но не db; его одного недостаточно для переноса. Учитываются Docker live-restore и containerd shims: остановленный daemon не доказывает отсутствие работающих контейнеров. Перед размонтированием проверяется отсутствие пользователей ФС; при неудаче операция останавливается, принудительное/lazy размонтирование не применяется. Аварийный stop должен быть доступен без чтения Compose/кода с уже отказавшего NVMe.

При отсутствии, подмене, read-only состоянии или ошибке NVMe:

- ОС eMMC продолжает загрузку до аварийного доступа; приложение и запись в БД/OTA блокируются;
- нет резервного перехода к пустым каталогам eMMC и автоматического создания новой базы;
- остановка/потеря mounts связана с остановкой writer-сервисов; I/O errors приводят к остановке записи и диагностике, а не к автоматическому форматированию или запуску `fsck` на смонтированном разделе;
- удалённый доступ не заявляется гарантированным при одновременной потере Wi-Fi; физический Recovery остаётся последним способом восстановления.

Веб-терминал Robopark зависит от приложения и NVMe. Аварийный доступ проектируется отдельно на ОС — например, защищённый SSH через заранее настроенный административный VPN. Выбор транспорта и доступа нужен до приёмки, но не требует дополнительного публичного Linux-терминала или ослабления TOTP в сайте. Текущий Tuna-сервис зависит от `/opt/robopark/current` и `robopark.service`, поэтому не является независимым recovery-каналом.

## OTA, удаление и смена схемы

Формат пакета OTA, SHA-256 и правила авторизации остаются текущими. Обновление Robopark не прошивает QSPI, eMMC, NVMe и не обновляет BSP/JetPack. Обновления ОС и приложения — разные операции с разными резервными копиями.

Настройка mounts хранится на уровне хоста и не включается в immutable Compose как новое расположение данных. Однако сохранение абсолютных путей само по себе ещё не доказывает обратную совместимость: нужна проверка установки host units, drop-ins, старых CLI, boot recovery и удаления. Первую версию с поддержкой storage layout следует явно обозначить. OTA на старый host agent, который может обойти guards или удалить mountpoints, блокируется проверкой возможностей либо получает отдельный совместимый переход; обычный откат приложения поддерживается в проверенных границах. Подпись издателя для этого не добавляется.

Удаление приложения показывает отдельный план удаления данных. Не удаляет сам раздел/файловую систему, чужие Docker volumes, корень `/srv/robopark-storage` или независимые средства восстановления. Изменять mounts разрешается только после остановки всех их пользователей. Повторная установка и восстановление сохранённых данных — отдельные сценарии; чистая установка не должна автоматически принимать старую БД.

Переключение `nvme-root` ↔ `emmc-nvme-data` не выполняется обычным OTA и не сводится к переключателю в интерфейсе: оно может требовать перепрошивки диска. До такой операции нужны внешняя проверенная копия и проверка restore; никаких обещаний сохранить раздел данных при flash.

Если на втором носителе уже осталась ОС, нельзя считать её автоматической безопасной резервной системой. До переключения нужны проверка порядка UEFI и запрет запуска старых production-служб при случайной загрузке старой ОС. Новая и запасная ОС должны иметь проверенную совместимость с общей загрузочной прошивкой; автоматический failover между ними не входит в базовую схему.

## Перенос с текущего хоста

1. На GEACX1 подтвердить загрузку, BSP, охлаждение, сеть и реальную схему дисков; подготовить выбранный layout. Зафиксировать точный исходный релиз и Alembic head резервной копии. Текущий restore требует равенства head: сначала восстанавливать на исходном релизе/head, затем выполнять штатную миграцию через OTA. Если исходный релиз не поддерживает новый storage guard, сначала нужен проверенный совместимый переход на старом хосте с созданием новой копии либо отдельный реализованный и проверенный сценарий forward-restore. Не подменять это установкой произвольной «последней совместимой» версии.
2. На старом хосте получить согласованную копию PostgreSQL и связанных файлов, конфигурации и секретов. Не копировать работающий PostgreSQL volume как обычную папку. Отдельно защищённо сохранить прежний `SECRET_KEY` и прочие действующие ключи шифрования, конфигурацию интеграций и нужные credentials; не публиковать их в Git/диагностике. TOTP и часть секретов хранятся в БД зашифрованными и без прежнего ключа не восстанавливаются.
3. Clean-install создаёт новый `SECRET_KEY`, а штатный restore не импортирует host credentials/config. Поэтому новый сервер держится в обслуживании: до запуска приложения с восстановленной БД перенести прежний ключ через отдельный защищённый импорт, атомарно обновить нужные конфиги и пересоздать потребителей настроек. Не заменять `host.env` целиком: профиль CPU/RAM, пути, origin и параметры новой БД остаются настроенными для GEACX1. Ротация ключа с повторным шифрованием не входит в базовый перенос. Проверить восстановление без активных внешних writer-интеграций: counts, вложения, вход владельца, TOTP, расшифрование секретов, права и фоновые операции на тестовых данных.
4. На финальном переносе остановить старые writer-процессы и синхронизировать согласованный финальный набор. Переключить Tuna и интеграции после проверки. Не запускать параллельно два production-бота/синхронизатора/туннеля с одной идентичностью.
5. Сохранить старый хост выключенным или изолированным для возврата. После первых записей на новом сервере возврат требует переноса актуальных данных; включение старой копии БД не является безопасным автоматическим откатом.

## Производительность, Wi-Fi и обслуживание

Сначала измерить текущий ресурсный профиль на плате. Лимиты API/БД — потолки, а не заранее занятая память. Оставить RAM для ОС, page cache, BuildKit и при необходимости отдельной очереди GPU. Число соединений БД и worker-процессов настраивать совместно. Не увеличивать их до числа ядер без измерений. Энергорежим и вентилятор выбирать по конфигурации GEACX1 и температуре, без автоматического постоянного MAXN/фиксации частот.

Compute-пакеты, NVIDIA Container Toolkit и GPU workload проверяются отдельно на совместимость с vendor R39.2.0. Модели и их кэши размещаются на NVMe. Будущий OCR/анализ изображений может использовать TensorRT, но SQL, HTTP и текущая обработка файлов от наличия CUDA автоматически не ускоряются. Не загружать GPU искусственно ради процента утилизации.

Для Wi-Fi проверить адаптер и драйвер, повторную ассоциацию, DHCP/DNS после разрыва, восстановление Tuna и отсутствие дублей фоновых операций. Потеря интернета не должна перезапускать PostgreSQL или удалять задания. Настройки power-save меняются только после измерения поведения конкретного адаптера. В recovery `POSTCHECK.sh` есть вывод IP-адресов, но нет проверки восстановления Wi-Fi и GPU workload.

На NVMe контролировать ёмкость ФС отдельно от ёмкости диска, SMART/температуру, ошибки I/O, inode, журналы, бюджеты сборок и резервных копий. Плановый TRIM проверяется на поддерживаемом SSD. На eMMC сохранять место для обновлений ОС и ограничить journald. Локальная копия на NVMe удобна для отката, но не заменяет копию на другом физическом устройстве/хосте.

## Приёмка обоих вариантов

| Проверка | Ожидаемый результат |
|---|---|
| Чистая установка и повтор после прерывания | Правильные device/UUID, отсутствие записи поверх чужой системы, предсказуемое продолжение |
| Перезагрузка каждого режима | Подтверждены boot device, BSP и фактическая ФС всех рабочих каталогов/volume БД |
| NVMe 1 ТБ после vendor flash | Размер APP и доступное место явно зафиксированы; не предполагаются по наклейке SSD |
| Холодный boot без/с другим NVMe в раздельном режиме | eMMC и аварийная сеть загружаются за ограниченное время, writers не стартуют, пустая БД на eMMC не создаётся |
| Docker socket, timers, ручной CLI | Нельзя обойти проверку хранения альтернативным способом запуска |
| Обслуживание и live-restore | DB/контейнеры/shims действительно остановлены перед переносом или размонтированием |
| I/O failure/read-only/заполненный диск | Операция завершается понятной ошибкой; не применяется небезопасный fallback |
| OTA и откат | Схема хранения и mounts сохраняются, version/data проверки проходят в обоих режимах |
| Удаление и повторная установка | Mountpoints и чужие данные защищены; удаление owned data только по показанному плану |
| Backup + restore | Совпадает исходный Alembic head, сохранён прежний ключ, работают TOTP/секреты/вложения и последующий OTA |
| Обрыв и восстановление Wi-Fi | Сайт/туннель возвращаются, задания не дублируются, БД не перезапускается из-за сети |
| Нагрузка на отдельном контуре | Короткие измерения latency, RAM, I/O и температур; без восьмичасового теста |
| Независимый аварийный доступ | В раздельном режиме реально работает без Docker и mounts приложения |
| Обновление прежнего хоста | Хост без storage manifest продолжает работать без NVMe и без автоматического переноса |

Сначала нужны автоматические проверки layout/state machine и интеграционные проверки systemd/mounts на Linux. Физическую загрузку GEACX1, NVMe, Wi-Fi и восстановление эти тесты не заменяют. Отключение диска/питания не испытывается на единственной рабочей копии production-данных.

## Последовательность реализации

1. Read-only discovery и отчёт по плате, дискам, backend Docker и существующим данным.
2. Подготовка выбранного layout, независимый guard и продолжение после прерывания; изменение clean-install и uninstall как одного контракта.
3. Интеграция guard с systemd, прямыми host operations, OTA/rollback и отображение схемы/ошибок в «Системе».
4. Восстановление и миграция данных, Wi-Fi/recovery-проверки и приёмка обоих режимов на GEACX1.
5. Настройка производительности по измерениям; отдельные GPU-функции — только под конкретную полезную задачу.

## Уточнения реализации rc.22

Реальная топология читается через `findmnt --task 1`: намеренно readonly namespace `ProtectSystem=strict` не считается отказом диска. Отдельная `robopark-storage-check.service` завершается до любых pre-start команд зависимых служб; локальные guards повторяют проверку. Независимый watchdog и запуск Docker проверяют наличие/UUID/RW без порога свободного места, чтобы очистка оставалась доступной. Новые операции, которым нужен запас места, проверяют его отдельно. Managed drop-ins дают только updater/commands запись в независимую копию guard на ОС.

Использованы контракты [findmnt --task](https://man7.org/linux/man-pages/man8/findmnt.8.html) и [systemd service ordering](https://man7.org/linux/man-pages/man5/systemd.service.5.html). Нативные службы хоста используют namespace PID 1; запуск storage CLI из контейнера не является поддерживаемой проверкой хоста.
