# Доступность ресурсов и очередь Mac · TEST RC15

Состав сети не фиксируется при установке. Tracker, Inventory и Emergency
проверяются отдельно: готовность Tracker не означает доступность двух других
сервисов, а отсутствие Inventory не отключает доступный Tracker.

| Состояние | Поведение |
| --- | --- |
| Сервер имеет доступ, Mac отсутствуют | Корпоративные чтения выполняются сервером; Mac для этого не требуется |
| Сервер не настроен для ресурса или временно недоступен | Используется готовый Mac разрешённого владельца с доступом к этой ручке |
| Доступен один Mac, в том числе на батарее | Лёгкие корпоративные чтения работают с ограниченной параллельностью и очередью |
| Доступно несколько Mac | Выбор учитывает доступ к операции, свободные слоты, задержку и ошибки; запрещено подменять владельца более привилегированным аккаунтом |
| Mac отключился во время чтения | В пределах исходного срока запрос может перейти на другой допустимый Mac или новое подключение того же устройства |
| Источника нет | Возвращается явная недоступность; сохранённые данные доступны только там, где реализован офлайн-кэш, и не считаются свежими |

Отказ в правах, отсутствие объекта и ограничение частоты не трактуются как
сетевой обрыв. Серверный бот-токен не передаётся Mac; личная авторизация Mac
не передаётся другим сотрудникам. Запись сохраняет отдельный протокол с
идемпотентностью: автоматический повтор чтения не разрешает слепой повтор записи.

Очередь ограничена числом активных запросов и сроком ожидания. Старые ожидающие
запросы имеют приоритет перед новыми на совместимом устройстве. Отмена и
истечение срока освобождают очередь и слот. Общий результат одинаковых чтений
не отменяет повторную проверку прав каждого получателя. Тяжёлые вычисления и
передача изображений сохраняют отдельные лимиты.

Heartbeat и проверка регистрации устройства получают отдельную ограниченную
очередь и потоки выполнения. Очередь пользовательских чтений не должна
вытеснять контроль связи: занятый Mac не считается отключённым лишь из-за
нагрузки на обработку запросов. Права владельца продолжают проверяться.

Локальное приложение периодически проверяет владельца корпоративной сессии.
Краткий сетевой сбой службы проверки не стирает уже проверенную авторизацию:
допускается не более часа с последней успешной проверки, без продления этого
времени при ошибках. Истечение известного срока токена, отказ в авторизации и
смена владельца прекращают использование соответствующей сессии. Новый вход
создаёт новую версию сессии даже при совпадении значения токена, поэтому поздний
ответ от старой проверки не может удалить новую авторизацию.

## Границы подтверждённой производительности

16 октября 2026 локальный синтетический стенд прошёл 200 отдельных сессий,
двух API workers и PostgreSQL 17: 2 000 запросов за 30 секунд, затем пакет
600 запросов с ограниченной параллельностью. Не было неожиданных ответов,
таймаутов, дублирования записей или нарушения проверяемой изоляции. Корпоративные
ответы искусственные; имитировались задержка 35 мс и потеря 1% попыток.
Временная БД находилась в tmpfs из-за заполненного диска Docker.

Отдельный тест Emergency с настоящим HTTP/WebSocket протоколом моделирует
200 пользователей, 20 роботов и один Mac с одним слотом на батарее. Одинаковые
чтения объединяются, разные ожидают свободный слот. Это подтверждает механизм,
но не производительность физического Khadas, Wi-Fi или корпоративных API.
Реальная приёмка TEST после OTA остаётся обязательной.

Живые проверки корпоративных ресурсов выполняются только на чтение. По
уточнению пользователя от 16 октября для ручной приёмки выбираются роботы
1000–3000; команды управления, изменение карточек и комментарии не выполняются.
