# Roadmap — Комплексная оптимизация Робопарк

**Дата:** 2026-09-19  
**Цель:** Сделать систему удобнее, быстрее, понятнее для 200+ одновременных пользователей на WiFi

## Критичные вызовы

### 🔥 Производительность под нагрузкой
**Проблема:** Сервер на WiFi, 200+ пользователей одновременно  
**Риски:**
- Медленные ответы API
- Перегрузка базы данных (SQLite)
- Конкуренция за WiFi bandwidth
- Потеря соединения у механиков в цеху

### 📱 Мобильный UX
**Проблема:** Механики работают на телефонах в полевых условиях  
**Риски:**
- Медленная загрузка на слабых устройствах
- Потеря данных при обрыве связи
- Неудобный интерфейс для работы одной рукой

### 🔄 Масштабируемость
**Проблема:** Рост количества парков и роботов  
**Риски:**
- Замедление запросов при большом объёме данных
- Неэффективные SQL запросы
- Отсутствие кэширования

## Фаза 1: Критичная оптимизация производительности (2-3 недели)

### 1.1 Backend оптимизация

#### Миграция с SQLite на PostgreSQL
**Почему:** SQLite не предназначен для 200+ одновременных подключений

**Действия:**
1. Настроить PostgreSQL с connection pooling (pgBouncer)
2. Мигрировать схему БД
3. Оптимизировать индексы для частых запросов
4. Настроить репликацию для read-only запросов

**Файлы:**
- `apps/api/src/robopark_api/db.py` — connection pooling
- `apps/api/alembic/versions/` — миграции
- `deploy/docker-compose.yml` — PostgreSQL контейнер

**Метрики:**
- Время ответа API: <100ms (сейчас ~500ms под нагрузкой)
- Concurrent connections: 200+ (сейчас ~50 max)

---

#### Кэширование на уровне API
**Почему:** Многие запросы повторяются (список парков, роботов, статусы)

**Действия:**
1. Внедрить Redis для кэширования
2. Кэшировать справочники (парки, роботы, пользователи)
3. Invalidation при изменениях
4. Cache warming при старте

**Файлы:**
- `apps/api/src/robopark_api/services/cache.py` (новый)
- `apps/api/src/robopark_api/middleware/cache.py` (новый)

**Метрики:**
- Cache hit rate: >80%
- Снижение нагрузки на БД: 60-70%

---

#### Оптимизация SQL запросов
**Почему:** N+1 queries, отсутствие индексов, неэффективные JOIN'ы

**Действия:**
1. Аудит всех SQL запросов (EXPLAIN ANALYZE)
2. Добавить индексы для частых фильтров
3. Использовать eager loading вместо lazy
4. Денормализация для критичных запросов

**Файлы:**
- `apps/api/src/robopark_api/routers/*.py` — все роутеры
- `apps/api/src/robopark_api/models.py` — индексы

**Метрики:**
- Количество запросов на страницу: <10 (сейчас ~50)
- Время выполнения запросов: <50ms

---

#### Rate limiting и throttling
**Почему:** Защита от перегрузки и DDoS

**Действия:**
1. Внедрить rate limiting per user/IP
2. Throttling для тяжёлых операций
3. Priority queue для критичных запросов

**Файлы:**
- `apps/api/src/robopark_api/middleware/rate_limit.py` (новый)

**Метрики:**
- Защита от перегрузки: 100%
- Fair usage: все пользователи получают ресурсы

## Риски и митигация

### Риск: Миграция на PostgreSQL сломает production
**Митигация:**
- Тестирование на staging
- Постепенный rollout
- Rollback план
- Dual-write период

### Риск: Offline-first усложнит код
**Митигация:**
- Использовать проверенные библиотеки
- Инкрементальное внедрение
- Тщательное тестирование
- Документация

### Риск: 200+ пользователей всё равно будет медленно
**Митигация:**
- Load testing на каждом этапе
- Горизонтальное масштабирование
- CDN для статики
- Мониторинг в production

## Следующие шаги

1. **Согласовать приоритеты** с командой и бизнесом
2. **Провести load testing** текущей системы для baseline
3. **Создать staging environment** для безопасного тестирования
4. **Начать с Фазы 1** — критичная оптимизация
5. **Измерять метрики** на каждом этапе

## Заключение

Это амбициозный план на 3-4 месяца работы. Ключевые принципы:
- **Измеряем всё** — метрики до и после каждого изменения
- **Инкрементально** — маленькие шаги, частые релизы
- **Пользователь в центре** — обратная связь от механиков
- **Надёжность** — нельзя сломать production

Результат: система, которая работает быстро и стабильно для 200+ пользователей, удобна для механиков и приносит бизнес-ценность.
