# Метаданные релиза и смена ключа OTA

## Проверяемые метаданные

Перед тегом релиза измените `deploy/release-metadata.json` в том же коммите, что код
миграций. Это данные JSON, не shell/Python-код. Публичные интерфейсы сборки:

```sh
scripts/pack-release.sh --metadata deploy/release-metadata.json artifacts/release.zip
python3 scripts/release_pack.py --root . --repository --version VERSION \
  --git-sha COMMIT --metadata deploy/release-metadata.json \
  --signing-key /protected/release-key.pem --output /outside-source/release.zip
```

`VERSION` и `COMMIT` во втором примере заменяются реальными значениями. Обёртка
использует корневой `VERSION` и Git SHA; при сборке из извлечённого релиза SHA
берётся из проверенного manifest или `ROBOPARK_RELEASE_GIT_SHA`.
Закрытый ключ хранится вне дерева исходников; его путь для обёртки задаётся через
`ROBOPARK_SIGNING_KEY_FILE`. Ключи здесь не создаются и не выводятся.

Обязательные поля: `migration_head` и `migration_compatibility` с точными ключами
`from_heads` (список уникальных исходных ревизий) и `reversible` (JSON boolean).
Укажите только проверенные исходные схемы. `reversible: true` — утверждение
ответственного за релиз о проверенной совместимости и пути восстановления, а не
результат автоматического анализа downgrade-функции. Для неизменённой схемы допустимы
`from_heads: []`, `reversible: false`. Изменение схемы без явной проверенной
совместимости OTA отклонит; упаковщик сам совместимость не придумывает.

Упаковщик статически разбирает `revision`/`down_revision` всех Alembic-миграций и
требует единственную фактическую вершину, равную `migration_head`, связный граф без
циклов и существующие `from_heads`. Код миграций для этой проверки не исполняется.
Устаревший необязательный `--migration-head` служит только дополнительной проверкой
равенства, не заменяет JSON. Неизвестные поля, дубли JSON-ключей и неверные типы
отклоняются. Необязательны `update_notes`, `min_installer_version`,
`required_capabilities`, `signing_key_rotation`; общие поля проверяют также API,
host и автономный verifier. Все значения входят в подписанный manifest.
GitHub workflow использует этот же файл и тот же упаковщик. E2E-кандидаты с новой
миграцией собираются через этот публичный интерфейс.

## Смена Ed25519-ключа через промежуточный релиз

Сначала установите обычный релиз с поддержкой этого контракта: старые версии с
закрытой схемой manifest не принимают поле смены ключа. Затем выпустите bridge
(промежуточный) релиз, **подписанный действующим старым ключом**, с добавлением:

```json
{
  "signing_key_rotation": {
    "next_public_key": "-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----\n",
    "activation_version": "1.2.3"
  }
}
```

Значение `activation_version` обязано точно совпадать с `app_version` bridge.
Предварительное объявление будущей версии не поддерживается. Принимается только
канонический публичный Ed25519 PEM, отличающийся от текущего ключа. Сам bridge
подписывается старым ключом; следующий релиз — новым. Поле смены ключа из metadata
следующего обычного релиза удаляется. В GitHub release environment и committed
`deploy/keys/release-public-key.pem` ключ меняют для **следующего** релиза, после
доставки bridge нужным хостам. Хост, пропустивший bridge, новый ключ не принимает.

Хост активирует новый ключ только после локальной готовности кандидата и проверки
схемы, до снятия maintenance. Авторитетное состояние root хранит в атомарном,
fsync-сохранённом `ops/state/signing-trust.json`; PEM и публичное свидетельство для
API — восстанавливаемые проекции. Сбой между записями завершается при recovery.
До подтверждения здоровья неудачный кандидат ключ не меняет. При откате до
возобновления записей восстанавливается прежнее состояние доверия. Первичная
установка bridge также активирует ключ только после локальной готовности.

Старый ключ остаётся допустимым только для точных подписанных manifest текущего и
предыдущего сохранённых деревьев (имя каталога + SHA-256 manifest). Он не даёт права
устанавливать новые архивы, включая будущие версии, подписанные старым ключом.
Если после bridge следующий релиз на новом ключе не прошёл проверку, откат к bridge
сохраняет новый ключ для последующей OTA. API со старым bind-mounted PEM проверяет
подписанное старым ключом свидетельство перехода; приватные ключи не передаются API.
Не удаляйте вручную trust state, pins или backup доверия в rollback-каталоге.

Автономная проверка следующего артефакта из исходного доверенного ключа возможна без
импорта кода из архива:

```sh
python3 verify-artifact.py --public-key old-public-key.pem \
  --trust-transition verified-bridge.zip successor.zip
```

Verifier проверяет bridge и sidecar-файлы старым ключом, затем следующий артефакт
новым и требует его версию выше bridge. Это проверка происхождения файла, а не
разрешение активировать ключ на хосте до readiness. Локальные Mac/fake-host тесты
проверяют контракт и сбои записей; проверка отключения питания, Docker/systemd/Tuna
на реальном Armbian и нагрузка 200 пользователей остаются целевой приёмкой.
