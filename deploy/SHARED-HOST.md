# Armbian 26 / 8 ГБ → Ubuntu 22.04 / 32 ГБ

Профиль рассчитан на Linux ARM64 или x86_64: Docker Engine с Compose plugin,
Python 3.10 или новее, curl, Tuna CLI, SSD и постоянное питание. 32-битная сборка Armbian
не подходит. Для БД и вложений используйте SSD, а не системную microSD.
Оставьте минимум 8 ГБ свободными для сборки; реальный запас должен вмещать
14 полных снимков, рабочие данные и временную копию самого большого снимка.

По умолчанию работают два API-процесса. Лимиты контейнеров: API 3 ГБ,
web 256 МБ, ops-agent 256 МБ; остальная память остаётся ОС, Docker и сборке.
Лимиты относятся к работающим контейнерам, не к сборке образов. Обновления
со сборкой выполняйте вне смены. На Ubuntu с 32 ГБ сначала оставьте тот же
профиль; `UVICORN_WORKERS=4` включайте только после замера на этом сервере.

## Первый запуск

Разместите эту версию проекта в `/opt/robopark`. Установите Docker Engine,
Compose plugin и Tuna CLI для архитектуры сервера. Не копируйте Mac `.venv`
или `node_modules` на Armbian: образы собирают зависимости для Linux.

```sh
cd /opt/robopark
sudo install -d -m 700 /etc/robopark /var/backups/robopark
sudo install -m 600 deploy/host.env.example deploy/host.env
sudo install -m 600 deploy/tuna.env.example /etc/robopark/tuna.env
sudoedit deploy/host.env /etc/robopark/tuna.env
```

В `host.env` задайте точный HTTPS-origin, новый Fernet `SECRET_KEY` и сильный
`SEED_PASSWORD` для первого royal. При переносе используйте прежний `SECRET_KEY`.
Не включайте `DEV_SEED`. В Tuna задайте токен и один постоянный домен или
зарезервированный поддомен. Значение CORS должно совпадать с публичным адресом.
API работает с UID 10001; ему нужен доступ к `host.env` для снимков, поэтому:

```sh
sudo chown 10001:10001 deploy/host.env
sudo chmod 600 deploy/host.env
sudo python3 deploy/host.py check
sudo python3 deploy/host.py start
curl --fail http://127.0.0.1:8080/api/health/ready
```

Проверка не выводит секреты. Она проверяет приватные права env-файлов,
HTTPS/cookie/ключ, отключённые demo-аккаунты, постоянный адрес Tuna,
Linux-архитектуру, свободное место, Docker и Compose. `start` собирает образы
и ждёт healthcheck. Сам туннель эта команда не публикует.
После первого входа удалите `SEED_PASSWORD` из env и выполните `host.py start --no-build`.

## Перезагрузка и ежедневный бэкап

```sh
sudo install -m 755 deploy/tuna-http.sh /etc/robopark/tuna-http.sh
sudo install -m 644 deploy/robopark.service /etc/systemd/system/
sudo install -m 644 deploy/robopark-backup.service /etc/systemd/system/
sudo install -m 644 deploy/robopark-backup.timer /etc/systemd/system/
sudo install -m 644 deploy/tuna.service /etc/systemd/system/robopark-tuna.service
sudo systemctl daemon-reload
sudo systemctl enable --now robopark.service robopark-backup.timer
# Публикует приложение по настроенному HTTPS-адресу:
sudo systemctl enable --now robopark-tuna.service
```

Бэкап запускается ежедневно в 04:15–04:25 по времени сервера и после пропуска
из-за выключенного ПК. Он использует существующий механизм снимков royal:
кратковременно включает обслуживание, сохраняет согласованную SQLite,
вложения и конфигурацию с ключом. Проверяет ZIP, manifest и SQLite quick_check,
затем копирует архив в `/var/backups/robopark` с правами 600.
Хранятся 14 последних успешных копий; повреждённая копия не запускает ротацию.
В Docker-томе остаётся последний подтверждённый автоматический снимок;
ручные снимки royal не удаляются. При одновременном обновлении/восстановлении
снимок отклоняется защитой общей операции: после завершения повторите бэкап.

```sh
sudo python3 /opt/robopark/deploy/host.py backup
sudo systemctl list-timers robopark-backup.timer
sudo journalctl -u robopark-backup.service --since yesterday
sudo python3 /opt/robopark/deploy/host.py status
sudo docker stats --no-stream
df -h /opt/robopark /var/backups/robopark
```

Копии содержат секреты. Переносите их также на отдельный защищённый носитель
или другой сервер: копия на том же SSD не спасает при его отказе. Раз в месяц
проверяйте восстановление на изолированной установке через royal → «Снимок и
обновление». Исходный архив, `host.env` и `/etc/robopark/tuna.env` сохраняйте
вне публичных каталогов. Tuna-токен не входит в снимок приложения.

## 200 одновременных пользователей

Результаты и воспроизводимый стенд описаны в [проверке нагрузки](../docs/capacity-benchmark.md).
Замер на Mac с локальными заменами Tracker/Emergency подтверждает работу
приложения в заданном сценарии, но не скорость Armbian, его SSD, канала или
настоящих внешних сервисов. До общего запуска повторите стенд на целевом ПК.
Он создаёт временную БД и тестовые сессии, не обращается к рабочим интеграциям.

Диагностика опрашивается примерно раз в 10–12 секунд, обычные данные — раз
в 30–36 секунд. Скрытые/offline-вкладки не опрашиваются; возвращение клиентов
распределяется во времени. `Retry-After` от 429 соблюдается, предыдущие данные
сохраняются. Общий кэш уменьшает запросы к внешним сервисам, но права доступа
проверяются заново для каждого клиента.

Tuna ограничивает домен **100 запросами в секунду**. Это включает статику,
входы и действия, поэтому 200 одновременных перезагрузок страницы могут получить
429 даже при быстром сервере. Первичную загрузку не следует путать с обычной
работой 200 открытых вкладок. Бесплатный динамический домен живёт 30 минут;
для смены нужен постоянный адрес. [Ограничения Tuna](https://tuna.am/docs/restrictions/),
[HTTP-туннели](https://tuna.am/docs/tunnels/http/).

Не открывайте наружу Vite `5173`, API `8000` или Docker socket. Публичный вход
идёт только через Tuna → localhost `8080`. Не задавайте `TUNA_RATE_LIMIT=20`
для этого профиля: нормальная суммарная частота опроса выше.

В Docker реальный IP может отображаться как адрес шлюза. Ограничение входа
применяется к паре «логин + IP», поэтому разные пользователи не делят один
лимит входа. Регистрация и аудит могут видеть общий адрес. Перед включением
саморегистрации проверьте передачу IP через установленную версию Tuna, включая
запрос с поддельным X-Forwarded-For. Не расширяйте доверие к заголовку на все
адреса. Учётные записи также можно создавать через администратора.

## Перенос на Ubuntu с 32 ГБ

1. Подготовьте `/opt/robopark` на Ubuntu с той же версией приложения. Соберите
   образы на новом хосте, настройте прежний `SECRET_KEY`, origin и защищённые
   env-файлы. Пока не включайте на нём Tuna.
2. Проверьте пробное восстановление свежего снимка на новом сервере и вход
   через локальный адрес/защищённый доступ. Для cookie Secure требуется HTTPS;
   используйте временный отдельный HTTPS-туннель с соответствующим CORS,
   вернув основной origin перед переключением.
3. В согласованное окно остановите Tuna на старом ПК, дождитесь завершения
   текущих действий, создайте финальный снимок командой `host.py backup`.
   Остановите старый Robopark командой `host.py stop`. Не запускайте его снова
   для записи после финального снимка.
4. Перенесите финальный ZIP защищённым способом. Через royal восстановите его
   на новом сервере; сохраните исходный ключ. Проверьте пользователей, парки,
   настройки интеграций, задачи, проверку робота и вложения. Не копируйте
   живые `.db`, `-wal`, `-shm` вручную.
5. Включите основной Tuna только на Ubuntu. Проверьте публичный HTTPS-вход
   обычного механика и ограничения его парка. Включите новый backup.timer,
   сделайте контрольный снимок. Старый хост оставьте остановленным.

Для отката без потери новых записей сначала остановите новый вход и перенесите
обратный свежий снимок на старый сервер. Простое включение старой БД после
работы на новой теряет сделанные после переключения изменения.
